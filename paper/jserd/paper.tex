\begin{abstract}
\textbf{Abstract}

AI coding agents produce code faster than a developer can review in detail,
and oversight collapses onto the automated test suite. When an agent says
``done'', nothing executes the checks it claims to have passed, and agents can
satisfy visible tests while missing the user's goal (reward hacking). This
paper presents Kata, an executable quality gate for AI-assisted software
changes. Kata guides a change through a nine-phase cycle --- FIT, THINK,
SIMPLIFY, INTENT, SURGICAL, VERIFY, TWIN CHECK, ARTIFACT, REPORT --- plus an
optional adversarial JUDGE that re-runs every claimed check and hunts eight
categories of fraud --- seven of them exercised by the evaluation --- such as
weakened tests, false completion claims, undeclared scope, and a triviality
claim the measured diff does not support. Unlike skills that instruct the
agent to be careful, Kata moves the objective parts of the discipline into
tested Python code: lint, typecheck when the project declares one, test, and
coverage read real exit codes, the JUDGE confronts the task file with the
repository, and an audit mode grades each phase as followed, skipped, faked,
or degraded. Two agent frontends are generated from a single source, and the
paper describes each executable phase as a code-anchored listing. Version
0.8.0 adds the declared typecheck role, execution evidence in the task file,
\texttt{kata --stamp} to close the JUDGE's diff window, strict project
configuration, and the eighth fraud category.

On 19 trap scenarios we wrote ourselves, the JUDGE returned every expected
verdict. In an executed comparison on the same scenarios, three related gates
also detected every planted fraud, so Kata's measured advantage is determinism
and cost (a median of 0.1\,s on fraud scenarios and 1.0\,s on the others), not
detection; ten of the eleven agent false positives fell on blind-spot
scenarios or on a Kata-specific diff convention. On 12 bug-fix tasks from
public repositories (48 agent sessions), the JUDGE's independent review
flagged the one case of undeclared scope and its own weakened-test detector
found none, but the sessions' own JUDGE runs falsely refuted six honest
fixes, under a rule corrected after the evaluated version. An appendix reports
an exploratory pilot and a 30-session campaign with an iterative
builder/critic loop built on the same task file and audit machinery; they do
not show that the loop improves the artifacts, and with one run per cell
their comparisons are inconclusive.

The scenarios are in-distribution for Kata; the judgment phases of the cycle
were not ablated and were evaluated only for cost; the JUDGE has reproduced
evasions for an agent that controls the repository; and whether the cycle
improves the quality of AI-assisted changes remains future work.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

AI coding agents (OpenCode, Claude Code, Cursor, and similar tools) change
software with remarkable speed. The hard problem is not the speed but whether
the result can be trusted. When an agent says ``done'', what sustains that
claim?

A skill says: \emph{``verify your tests before committing''}. The model may
follow, ignore, or half-follow the instruction, and nobody can tell the
difference. An agent can claim ``lint clean, tests passing, coverage at the
gate'' without any of it having been executed. Or worse: it can have executed
the checks, but with a weakened test (a \texttt{pass} in place of the
assertion) that ``passes'' without verifying anything.

The Karpathy Development Cycle --- the name this paper gives to the
agentic-engineering discipline described by Karpathy
\cite{karpathy} --- proposes discipline: think
before coding, keep the code minimal, make surgical changes, and verify
objectively. The Fable
Method \cite{fable}, a GitHub repository that has not been peer-reviewed,
proposes gates: classify the task before acting (fit
gate), require evidence before action, verify adversarially, and report
outcome-first. Both are methodologies, and a methodology is text that
instructs. Text instructs; it does not execute.

This paper presents Kata (``form'' or ``pattern'', as in a martial arts
kata: a disciplined, repeatable sequence of movements), a quality gate for
software changes assisted by AI agents. Kata's contribution is to move the
objective parts of the discipline out of the prompt and into executable,
testable Python code. The lint, test, and coverage steps read real exit codes;
the JUDGE re-runs claimed checks against the real repository, including
committed and untracked files; and the audit mode grades each phase of a
completed task as followed, skipped, faked, or degraded, naming the concrete
risk each grade other than followed created. Where a skill prescribes honesty,
Kata supplies an executable mechanism to verify it.

This paper is a \textbf{software article}. Following the journal's
guidelines (quoted in Section~\ref{sec:exec-comparison}), it describes a
tool, positions it as a significant advance over
previously published software, and demonstrates the advance by \emph{direct
comparison with available related software}: Section~\ref{sec:exec-comparison}
reports an executed comparison in which Kata and three alternative gates
(nova \cite{nova}, claude-wizard \cite{claudewizard}, and a prompt-only
baseline) review the same 19 adversarial scenarios. All four detected the
planted frauds; the comparison locates Kata's measured advantage in
determinism and cost --- the same verdict every run, at about one second per
review on the trap scenarios. Kata also made no false accusations, but most agent false positives
fell on scenarios built around Kata's own conventions, so that result is not
evidence of superior reviewer restraint.

The evaluation answers three research questions, each tied to the evidence
that answers it:
\begin{itemize}
\item \textbf{RQ1.} Does the JUDGE honour its two-sided contract ---
detecting planted frauds without accusing honest work, and confessing what
it cannot observe? (Section~\ref{sec:self-check}: 19 trap scenarios.)
\item \textbf{RQ2.} How does the JUDGE compare with related gates reviewing
the same scenarios, in detection, false accusations, determinism, and cost?
(Section~\ref{sec:exec-comparison}: 19 scenarios, four gates.)
\item \textbf{RQ3.} Is the cycle feasible on real repositories we did
not write, and what does it cost? (Section~\ref{sec:external-evaluation}: 12
real bugs, 48 agent sessions.)
\end{itemize}
The evaluation does not establish whether the judgment phases of the cycle
(THINK, SIMPLIFY, INTENT, SURGICAL, TWIN CHECK) improve the changes an agent
produces: they were not ablated, and their contribution was measured only as
cost. Appendix~\ref{sec:gauntlet-pilot} reports an exploratory fourth
question, outside the gate's evaluation: can an iterative builder/critic loop
be carried and audited by the same task file, and does it improve the
artifacts? The first half is answered affirmatively. The second finds no
evidence of improvement, and no power to exclude one, across a 24-session pilot
and a 30-session campaign (54 matched pairs, of which 19 were byte-identical
and 35 were judged), so the question remains open with a better-instrumented
path to it.

Section~\ref{sec:field} places Kata in the context of related work.
Section~\ref{sec:design} describes the software design and the trade-offs

Section~\ref{sec:discussion} discusses the findings and their limitations.
Section~\ref{sec:threats} states the threats to validity.
Section~\ref{sec:conclusion} concludes, and Appendix~\ref{sec:gauntlet-pilot} reports the exploratory loop study.

\section{Statement of need}
\label{sec:need}

AI coding agents produce code faster than a developer can review in detail, and the
oversight surface collapses onto the automated test suite. Reward hacking
naturally arises in this setup: agents optimize for passing visible tests
while deviating from the user's true goal. SpecBench \cite{specbench}
measures this phenomenon and finds that the gap between visible and held-out
test suites grows by 28 percentage points for every tenfold increase in code
size, with failures ranging from subtle feature isolation to deliberate
exploits, including a 2,900-line hash-table ``compiler'' that memorizes test
inputs. Agents also end failure transcripts with ``all tests pass'', and
tests get weakened until they agree with the code \cite{fable}.

Large language models cannot reliably self-correct without external feedback
--- sometimes their performance even degrades after self-correction
\cite{selfcorrect}. The implication is that verification cannot be left to
the model checking itself: it must be external, executable, and objective.

The target audience of Kata is developers, researchers, and teams who use AI
agents to modify code and need objective, reproducible verification that
what was claimed was actually done. Kata is a quality gate for software
changes, not a project template. It fits the following situations:

\begin{itemize}
\item \textbf{Before committing}: run the full cycle to force evidence for
the change --- problem, assumptions, minimality, intent agreement, and
passing lint, tests, and coverage --- instead of committing on an ``it works''
impression.
\item \textbf{Bug fixes}: the cycle is adversarial about defects. INTENT
catches code/test/specification conflicts, and TWIN CHECK searches the
project for the same defect pattern elsewhere, recording even a negative
result.
\item \textbf{Small code-loop tasks}: the FIT gate measures the diff and
routes trivial changes (one file, fewer than ten lines) directly, without
planning ceremony.
\item \textbf{Planning before implementation}: \texttt{kata --plan} runs FIT
and THINK, saves the plan with assumptions and unknowns, and stops --- the
plan can be reviewed or handed off before a single line changes.
\item \textbf{Adversarial verification of finished work}:
\texttt{kata --judge} re-runs every claimed check and hunts eight fraud
categories before a merge or hand-over.
\item \textbf{Auditing tasks after the fact}: \texttt{kata --audit} grades
each phase of a completed task as followed, skipped, faked, or degraded, and
names the concrete risk each grade other than followed created.
\item \textbf{Continuous integration}: \texttt{kata --check-only} runs lint,
tests, and coverage with the coverage gate, non-interactively, as a CI entry
point.
\end{itemize}

Equally important is defining what Kata is \emph{not}. Kata is not an agent
that synthesizes code: it does not generate patches or prompt language
models to implement algorithms. It is not an automated test generator: it
does not synthesize test suites or infer formal invariants. Nor does it
claim to solve the general test oracle problem \cite{barr-oracle}: it takes
the repository's declared verification commands and test suite as the
material ground truth, ensuring that claimed checks were genuinely executed
and that declared assertions were executed and not syntactically weakened. Kata is thus a
verification quality gate and evidence-forcing scaffold, leaving code
synthesis to the agent or human developer.

\section{State of the field}
\label{sec:field}

Several tools and methodologies address disciplined AI-assisted development.
The Fable Method \cite{fable} is the closest conceptual ancestor: it defines
a think/act/prove loop with a fit gate, a triviality gate, evidence before
action, adversarial verification, and outcome-first reporting, and it ships
an eval that keeps the method honest. Kata adapts the fit gate, the
triviality gate, the intent gate, and the hard bounds directly from it, but
differs in one structural way: the objective logic lives in a Python package
(\texttt{kata.fit}, \texttt{kata.verify}, \texttt{kata.judge}) that is
unit-tested and measured for coverage, rather than in prompt text. The
Fable Method's own \texttt{fable-judge} also treats a report as a set of
claims and hunts weakened tests; the structural difference is that it is
prompt text, while Kata's judge is a Python program whose verdict is
computed from exit codes, the Git diff, and a Git-anchored baseline, and
whose detection is measured by the public trap suite.

claude-wizard \cite{claudewizard} is an 8-phase development skill with TDD
and adversarial review, but it is a skill only: there is no backend that
executes the gates. Ring \cite{ring} is a large skills library (76 skills, 33
agents) that enforces engineering practices with 10-gate development cycles,
again as instructions rather than executable checks. nova \cite{nova}
provides pre-commit quality gating, but as an agent skill without a shared
executable core. On the research
side, SpecBench \cite{specbench} measures reward hacking in coding agents, and
SWE-bench \cite{swebench} benchmarks agent capability on real GitHub issues;
both measure agents, neither provides a gate that a team can run on its own
changes.

The problem itself predates coding agents. Specification gaming ---
optimizing the measured proxy instead of the intended goal --- is
documented across machine learning \cite{krakovna, amodei-concrete} and
formalized as variants of Goodhart's law \cite{goodhart}. Software
engineering has studied its counterpart for decades as the oracle problem:
a passing suite is only as meaningful as the oracle behind it
\cite{barr-oracle}, which is why independent oracle techniques such as
metamorphic testing exist \cite{chen-metamorphic}. Reward hacking in
coding agents is this same failure with a compiler attached, and Kata's
answer is to treat each claim in the task file as a property and the
repository as the oracle, re-executing the claim instead of reading it.

Three considerations led us to build Kata rather than contribute to an
existing project. No existing tool ships an executable verification engine:
the closest alternatives are prompts that ask the model to verify itself,
which the self-correction literature shows is unreliable \cite{selfcorrect}.
Kata also needed to serve two agent hosts (OpenCode and Claude Code) with
identical behavior, and a single Python backend with generated frontends
guarantees that the checks a task claims to have passed are the same checks
in both hosts. The third consideration was self-verification: Kata's own
lint, tests, and coverage are measured, and in the evaluated version
(defined in the Declarations) 19 adversarial trap scenarios ran in continuous integration to
check that the JUDGE catches planted frauds and does not accuse honest
work; the current release, 0.8.0, runs 25.

\subsection{Recent research on agent verification}

The research landscape of 2026 has produced several works that corroborate
the problem Kata addresses and sharpen its positioning. We note up front
that most of the 2026 citations in this subsection are arXiv preprints
(not yet peer-reviewed; the bibliography marks them); they are cited as
evidence of an emerging research direction, not as established results,
and the claims we draw from them are qualitative positioning, not
measured premises. The Unreliable
Progress Bar study \cite{unreliable-progress} shows that LLM agents cannot
reliably report task progress throughout execution --- agents claim
completion states that do not match reality, and the JUDGE re-executes
claims of that kind. The Double Measurement Confound
\cite{double-measurement} demonstrates that agent benchmarks suffer from
de-scaffolding and ground-truth scoring confounds, arguing that reliability
must be measured beyond the mean; Kata's trap suite follows the same
principle by testing both fraud detection and false-positive avoidance.
XAgent \cite{xagent} uses execution-guided agentic AI for issue
localization and resolution, showing that execution feedback improves agent
outcomes --- the same insight that motivates Kata's decision to read real
exit codes rather than model intentions. Consort \cite{consort} is a
spec-first agent framework for enforced, test-driven development on live
database branches; it shares Kata's enforcement philosophy but is scoped to
database development, while Kata is a general-purpose gate. The Authority
Is Not a String harness \cite{authority-harness} scopes agent capabilities
to resist prompt injection, complementing Kata's authorization gate (AUTH
line) from the security angle. TrajMark \cite{trajmark} attributes ownership
and localizes tampering in coding-agent trajectories, which is conceptually
adjacent to Kata's baseline tampering detection, though applied to
trajectory provenance rather than task files. The Discovery Certification
Protocol \cite{discovery-certification} audits AI research agents by
certifying that claimed discoveries are reproducible --- the same
claim-vs-reality confrontation that the JUDGE performs for software
changes. RefVerifier \cite{refverifier} semi-automatically verifies
reference claims in scientific manuscripts, another instance of the
claim-verification pattern. The study on traditional test criteria
for LLM-generated code \cite{test-criteria-llm} and the dynamics of
iterative bug-fixing with LLMs \cite{not-buggy} both show that verification
of AI-generated changes requires more than passing tests --- the former
because traditional criteria miss LLM-specific bugs, the latter because
agents may fix what is not broken. Together, these works are consistent with
Kata's core design decision: verification should be external, executable, and
claim-based, not self-reported. They do not test it.

across eight categories, post-hoc auditing, and blind-spot confession.

Two qualifications bound the comparison. Consort \cite{consort} executes

changes it is not directly comparable by execution, so Section~\ref{sec:exec-comparison}

qualification concerns \emph{executing verification}: the \texttt{kata} CLI

runs checks and reads exit codes. Their ``Partial'' fraud column
reports that the adversarial step exists only as instruction text --- and
the executed comparison shows that a reviewer carrying that instruction can
run the checks when prompted, which is why the measured difference lies in
determinism and cost rather than in detection
(Section~\ref{sec:exec-comparison}).

\section{Software design}
\label{sec:design}

Kata's design is organized around one principle: the parts of the cycle that
can be objective must be executable, and the parts that cannot must be
declared before the evidence exists. The Python package \texttt{src/kata/}
implements the objective logic in four modules.

Figure~\ref{fig:cycle} shows the complete cycle. The nine phases run in
sequence, with the optional JUDGE applied after REPORT. The phases that
can be objective (FIT, VERIFY, JUDGE) are backed by executable Python
logic; the phases that require judgment (THINK, SIMPLIFY, INTENT,
SURGICAL, TWIN CHECK, ARTIFACT, REPORT) are guided by skills and recorded
in the task file, which the objective phases read and confront with the
repository.

Architecturally, Kata operationalizes this discipline along two distinct usage tiers:
(1) an \emph{interactive authoring scaffold} (\texttt{kata --task}), which guides the developer or agent step-by-step through the nine-phase cycle, generating structured evidence, enforcing minimality, and anchoring baseline commits in the task file; and
(2) a \emph{decoupled reviewer gate} (\texttt{kata --judge} and \texttt{kata --check-only}), which operates non-interactively, re-executing verification commands and auditing repository diffs against baseline anchors. This architectural separation ensures that while the authoring cycle provides deliberate friction and governance for complex, open-ended tasks, automated pipelines and routine pre-commit workflows can deploy the verification gate (without the anchor-protection that \texttt{--trusted-base} adds in CI, Section~\ref{sec:threat-model}), which took a median of about two seconds per change on the real repositories of Section~\ref{sec:external-evaluation}.

\subsection{Architecture}

\texttt{kata.fit} measures the real diff against \texttt{HEAD} (including
untracked files) and applies the triviality gate (at most one changed file
and fewer than ten changed lines); Listing~\ref{alg:fit} describes the
diff measurement and the gate. \texttt{kata.verify} runs lint, a declared
typecheck, tests, and coverage with a numeric gate, reading exit codes rather
than model intentions (Listing~\ref{alg:verify}); a declared role in
\texttt{.kata/config.yaml} runs verbatim, so
the tool does not assume the target project is Python.
\texttt{kata.judge}
treats the task file as a collection of claims, re-runs the claimed checks,
diffs the claims against the repository, and hunts eight fraud categories:
weakened checks, false completion, scope creep, unauthorized actions,
specification betrayal, debris, baseline tampering, and a triviality claim
the measured diff does not support
(Listings~\ref{alg:judge}--\ref{alg:weakened}). The evaluated version hunted
the first seven; the eighth was added in 0.8.0. \texttt{kata.cli}
orchestrates the nine phases, persists the task file, and exposes the audit
and judge modes (Listing~\ref{alg:cycle}). Section~\ref{sec:algorithms}
presents these algorithms in full as numbered Listings.

\subsubsection{Language-agnostic verification}

Kata does not assume the project it verifies is a Python project. The
project itself knows how to check its repository, so the commands live in
\texttt{.kata/config.yaml}, next to the task files:

\begin{lstlisting}[caption=Declaring the verification commands of a non-Python project.]
verify:
  lint: npx eslint src tests
  test: npx vitest run
  coverage: npx vitest run --coverage
  coverage_pattern: 'All files\s+\|\s+([\d.]+)'
  gate: 80
\end{lstlisting}

Every key is optional. A role that is not declared falls back to the
Python default for that role (ruff, pytest, pytest-cov) and keeps obeying
the path flags, so a project can replace only its linter and keep pytest.
The exception is \texttt{typecheck}: there is no universal type checker, so
an undeclared typecheck does not run and \texttt{verify.typecheck\_clean}
stays \texttt{null}, never \texttt{true}. A declared role is run verbatim
and judged by its exit code, the one contract every lint and test tool
honours. Coverage is the other exception: the built-in path delegates the
gate to \texttt{--cov-fail-under}, which does not exist outside Python, so a
declared coverage command has its percentage extracted with
\texttt{coverage\_pattern} and compared here. If the pattern matches nothing,
the check fails rather than recording 0.0\% as a pass --- ``could not
measure'' is not ``measured and passed''. When the project declares several
coverage sources, all of them are passed to pytest-cov, so the gate measures
the surface the project declared rather than a subset of it.

A config file that exists but is invalid aborts with exit code 1. Falling
back to ruff silently would report the success of a check the project
never asked for, and that is the kind of fabricated claim the judge
exists to detect. Since 0.8.0 the refusal is stricter: an unknown key at
any level is a named error, because a misspelled section
(\texttt{veirfy:}) used to fall back to the Python defaults with no
warning, and a command containing a shell operator (\texttt{\&\&},
\texttt{||}, \texttt{|}, \texttt{;}, \texttt{>}) is refused as well.
Commands run without a shell, so \texttt{npm run check \&\& npm run test:db}
would reach npm as arguments and exit 0 with the second tier never
executed; the project must declare a script or an explicit
\texttt{bash -c}. A path flag that no longer applies because its role is
declared is reported as ignored instead of being silently discarded.
The
JUDGE follows the same line: it knows the test syntax of Python, JS/TS,
Go, Ruby, Rust, Java/Kotlin, C\#, PHP, and Swift (the language probes
implemented in \texttt{kata/judge.py} as a per-language table of
\emph{weakened}, \emph{empty-body}, \emph{no-op}, and
\emph{assertion-family} patterns). A language outside this
list (for example, Elixir \texttt{.exs}) becomes a declared blind spot,
not silence. The 70\% coverage gate that the built-in verification default
uses is a project convention carried from Kata's own repository, not a
research finding: the effective gate is resolved per run as the
\texttt{--gate} flag if given, then \texttt{verify.gate} from
\texttt{.kata/config.yaml}, then 70\%,
and the JUDGE compares the measured coverage against whatever gate the
project ended up with (Section~\ref{sec:usage}).

The frontends are generated, not hand-maintained. The phase prompts live
once in \texttt{phases/*.md} and are rendered into the OpenCode agent and
the Claude Code skills by a build script (\texttt{scripts/build\_skills.py}),
following the same single-source discipline that Section~\ref{sec:algorithms}
applies to the executable modules. Structurally, the frontends adapt to each
host's execution model: in OpenCode, Kata provides an autonomous orchestrator
agent (\texttt{@kata}) and individual phase skills; in Claude Code, where an
isolated subagent would conceal the interactive questions from the main
dialogue, Kata runs directly in the primary conversation through skills
alone (\texttt{skills/kata/} orchestrating the phase skills).
The script measures the shared
fraction by rendering every source for both frontends and diffing the
outputs line by line: 92.8\% of the rendered lines are shared at tag
\texttt{v0.8.0} (93\% at whole-number precision), and the remainder is
declared difference --- host
tool names, identity wording, and capability blocks such as the
closed-choice ask --- reported by
\texttt{python3 scripts/build\_skills.py -{}-stats}. The figure moves as the
phase sources grow: the same command reported 92.6\% at \texttt{v0.7.0} and
92.8\% at \texttt{v0.8.0}. The 395 divergent
lines are the count we observed between the two hand-maintained
copies before the single-source migration; that figure is historical and
the script does not re-derive it. This
single-source design exists because the previous arrangement --- two
hand-maintained copies --- failed: the copies accumulated those 395
divergent lines, including an improvement applied to one frontend and
forgotten in the other. A test fails when the generated files drift from
the source, so the divergence cannot pass unnoticed.

\subsubsection{Domain adapters}

Kata extends the cycle to non-coding tasks without changing the underlying
pipeline through domain adapters. A task declares its domain in the task
file (\texttt{domain: devops}, for example); the orchestrator loads the
adapter after FIT and applies its domain-specific evidence set and fraud
table. Each adapter defines: the domain scope (what it covers and
explicitly does not cover), the evidence (files and state to inspect before
acting), the authority (who decides correctness in the domain), how to
verify by observation, a domain-specific fraud table, a binding minimum
evidence set, FIT routes by task shape, and red lines (actions never
allowed without documented human authorization).

Adapters are optional: a missing adapter does not fail \texttt{--doctor}
or stop the cycle, because the default domain is \texttt{coding} and most
tasks do not need an adapter. When a domain adapter is missing for a
non-coding task, the orchestrator records the skill name in
\texttt{preflight.skills\_missing} and falls back to the adapter's minimal
contract. Kata ships four domain adapters: \texttt{kata-devops} (Docker,
Docker Compose, Terraform, Nginx, GitHub Actions, deploys, and
healthchecks), \texttt{kata-data-analysis} (pandas, notebooks, SQL,
dashboards, and data pipelines), \texttt{kata-research} (bibliographic
search, literature review, and academic synthesis), and \texttt{kata-docs}
(READMEs, technical specifications, and architecture guides). New adapters
follow the canonical schema in \texttt{domains/TEMPLATE.md} and are
compiled to both frontends by the same build script that generates the
phase skills, so an adapter is written once and served to both hosts.

\subsection{Design trade-offs}

The cycle encodes two design trade-offs.

The first is the \textbf{done criterion} (Fable Step 1): THINK records what
``ready'' means and how it will be verified \emph{before} the evidence
exists, and VERIFY confronts that declared criterion with the final result.
Without this, the success criterion only exists after the work is done, and
``is it satisfied?'' becomes unfalsifiable.

The second is the \textbf{hard bound} (Fable Step 5): after three failed
verification attempts the task is handed back to the user with what was
tried, the real output, and the current hypothesis, instead of looping
fix-verify forever. The JUDGE also confesses its blind spots: if it could
not observe something (a test language it has no probes for, a file outside
the diff), the verdict is UNVERIFIABLE, never VERIFIED --- ``I could not
look'' is never reported as ``all clear''.

\subsection{The claim-based verification model}

The JUDGE's design is organized around a claim-based verification model
that distinguishes Kata from both prompt-based skills and benchmark
harnesses. A task file is treated as a collection of claims --- ``lint
clean'', ``tests pass'', ``coverage at the gate'', ``two files changed
surgically'', ``intent aligned'' --- and each claim is confronted with the
repository in one of three ways:

\begin{itemize}
\item \textbf{Re-executed}: lint, tests, and coverage are re-run and their
exit codes compared with the claimed results. A claim that fails
re-execution is a false completion fraud.
\item \textbf{Confronted with the diff}: surgical scope and intent
alignment are checked against the actual changed files. A file changed but
not declared is scope creep; an intent gate that recorded disagreement but
was approved anyway is specification betrayal.
\item \textbf{Accepted without verification}: the success criterion is a
subjective confirmation the user gives during VERIFY, and no command
reproduces it. The JUDGE lists it separately as accepted without
verification, and it adds a caveat. Counting it as verified is the fraud
the judge exists to hunt.
\end{itemize}

This three-way classification keeps the JUDGE honest in both
directions. It does not over-claim: claims it cannot re-execute are
confessed, not assumed. Neither does it under-claim: claims it can
re-execute are always re-run, never taken at face value. The same model
applies to the audit mode, which grades each phase as followed, skipped,
faked, or degraded by comparing the task file's content with what the phase was
supposed to record. Section~\ref{sec:algorithms} makes the objective
logic behind these phases explicit: Listings~\ref{alg:fit}--\ref{alg:traps}
describe, in a readable form, exactly what each executable phase computes,
so the description of the tool and the tool itself can be compared.

The claim-based model also connects Kata to the broader verification
literature: the same pattern has emerged independently in other domains, as
Section~\ref{sec:field} surveys and Section~\ref{sec:discussion} develops.
Kata's contribution is
to apply the claim-verification pattern to the software change itself,
where the claims are the task file and the ground truth is the repository.

\subsection{Descriptive algorithms}
\label{sec:algorithms}

The objective phases of the cycle are executable Python. This subsection
presents, as numbered Listings, a readable, implementation-oriented
description of the algorithm behind each executable module. Each Listing
is anchored to the code as cited in the Declarations (commit
\texttt{230e81a} of the evaluated version); line references
are from that revision.

\paragraph{Fit gate.} Listing~\ref{alg:fit} measures the real diff a task
brings and applies the triviality gate. The critical detail is that Git's
\texttt{diff} --- unstaged, staged, or against a commit --- is blind to
files that never entered the index, so \texttt{untracked\_stats} counts the
lines of untracked files explicitly (\texttt{kata/fit.py:23}). A file that
cannot be inspected (binary, or larger than
\texttt{MAX\_UNTRACKED\_FILE\_BYTES} = 256\,KiB, \texttt{kata/verify.py:63})
counts as ten lines, which is exactly the number that fails the triviality
gate: ``could not look'' must not become ``trivial change'', or the cycle
would skip SIMPLIFY, INTENT, and SURGICAL where there is the
least evidence to trust.

\begin{lstlisting}[caption=fit gate (kata/fit.py).,label=alg:fit]
ALGORITHM fit_gate(cwd)
  // diff_stats: real diff against HEAD, including untracked files
  1  files <- []
  2  lines <- 0
  3  result <- git diff HEAD --name-only       // staged + unstaged
  4  if result failed then result <- git diff --name-only
  5  if result failed or output empty then result <- git diff --cached --name-only
  6  files <- non-empty lines of result.stdout
  7  for each line of git diff HEAD --stat (or fallback variant):
  8      if line matches |<N>        then lines <- lines + N
  9  (new_files, new_lines) <- untracked_stats(cwd)
 10  files <- files union new_files
 11  return (files, lines + new_lines)

  // untracked_stats: untracked files are invisible to every git diff
 12 for each f in untracked_files(cwd):            // git ls-files --others
 13     if not is_inspectable(f)                    // binary or > 256 KiB
 14         then new_lines <- new_lines + 10        // "cannot look" fails the gate
 15     else count utf-8 lines of f, summing into new_lines
 16     on OSError/UnicodeDecodeError: new_lines <- new_lines + 10

  // triviality gate (fable-method)
 17 is_trivial(files, lines) := len(files) <= 1 AND lines < 10
\end{lstlisting}

\paragraph{Verification pipeline.} Listing~\ref{alg:verify} runs the three
roles of the evaluated version --- lint, test, coverage --- respecting the
project's declared commands from \texttt{.kata/config.yaml} when present
(\texttt{config.py}), and falling back to the Python defaults otherwise. The
0.8.0 pipeline adds the declared \texttt{typecheck} between lint and test;
it has no default and does not run when undeclared. Three properties are
deliberate. A declared role runs verbatim and is judged by its exit
code, the one contract every lint and test tool honours. Coverage
is short-circuited when the test step fails, since a coverage number on top of a
failing suite is deceptive and uninformative. And ``could not measure'' is never recorded as
``measured and passed'': when the coverage pattern matches nothing, the
check fails with a named error instead of reporting 0.0\% as a pass
(\texttt{verify.py:201--207}).

\begin{lstlisting}[caption=verification pipeline (kata/verify.py).,label=alg:verify]
ALGORITHM run_all(ruff_paths, test_paths, ignore, cov_source, gate, config)
  1  cfg <- config or VerifyConfig()     // roles from .kata/config.yaml
  2  if cfg.lint declared  then ruff <- run_command(cfg.lint)       // verbatim, exit code
  3                      else ruff <- run_ruff(ruff_paths)          // python -m ruff check
  4  if cfg.test declared  then pytest <- run_command(cfg.test)
  5                       else pytest <- run_pytest(test_paths, ignore)
  6  if pytest.ok:
  7      if cfg.coverage declared  then coverage <- run_command_coverage(cfg.coverage,
  8                                                                     pattern, gate)
  9                              else coverage <- run_coverage(source,
 10                                                             test_paths, gate)
 11  else coverage <- FAIL("skipped - tests failed")   // short-circuit
 12  return {ruff, pytest, coverage}

  // built-in coverage: gate delegated to pytest-cov --cov-fail-under
 13 run_coverage: cmd <- pytest <test_paths> --cov=<src>...
 14               --cov-report=term-missing --cov-fail-under=<gate> -q
 15               ok <- (exit code 0)  AND  TOTAL line matches
 16               ^TOTAL\s+.*?(\d+(?:\.\d+)?)%    // else FAIL, never 0.0% pass
 17 // declared coverage: percentage extracted by pattern and compared here
 18 run_command_coverage: match <- re.search(pattern, output)
 19   if no match or no capture group or group not numeric: FAIL (named error)
 20   ok <- (exit code 0) AND float(match[1]) >= gate
\end{lstlisting}

\paragraph{Cycle orchestration.} Listing~\ref{alg:cycle} is the interactive
driver (\texttt{kata/cli.py}). It persists the task file after every phase
with an atomic write (\texttt{mkstemp} + \texttt{fsync} + \texttt{replace},
\texttt{cli.py:115}), so an interrupted cycle can be resumed. The routes
matter: a trivial task skips THINK through SURGICAL via the triviality
gate; \texttt{--plan} and the \texttt{plan-first} route run THINK and
stop, leaving a plan; the \texttt{question} route also runs THINK and
stops, leaving a diagnosis. The verify step implements
the hard bound of Fable Step 5: a counter of \emph{failed} attempts
persisted in the task file hands the task back to the user after three
failures.

\begin{lstlisting}[caption=cycle orchestration (kata/cli.py).,label=alg:cycle]
ALGORITHM main()
  1  parse args; reject mutually exclusive modes; validate task name
  2  if --doctor then print skill install per frontend; exit 1 iff partial
  3  mkdir .kata/; config <- load_verify_config()       // ConfigError -> exit 1
  4  gate <- --gate flag else config.gate else 70
  5  cov_source <- --cov-source else pyproject [tool.coverage.run] source else "src"
  6  branch by mode:
  7    --init TASK:  create template; capture base_commit + git anchor
  8                  refs/kata/base/<sha256(task)>; run FIT, THINK; save; stop
  9    --report:     outcome-first report; exit 1 iff status rejected
 10    --judge:      judge_task(); print verdict; exit 1 iff REFUTED
 11    --audit:      grade phases; exit 1 iff any phase not followed
 12    --check-only: run_all(); exit 0 iff approved
 13    default:      pick task (branch name > menu > new); run cycle:
 14      FIT
 15      if trivial or plan or route in {question, plan-first}: THINK
 16      if route == question:      stop
 17      if plan or route == plan-first: stop (plan saved)
 18      if not trivial: SIMPLIFY, INTENT, SURGICAL      // judgment phases
 19      VERIFY                       // hard bound: hands back after 3 failures
 20      if not trivial: TWIN CHECK   // approved tasks only
 21      ARTIFACT, REPORT
 22  after each phase: save task file (atomic write)

  // VERIFY in detail
 23 results <- run_all(...); print lint/test/coverage with real exit codes
 24 success_criteria_met <- user confirms (or True in --check-only)
 25 attempts <- persisted count of FAILED runs, not executions
 26 if not all_ok: attempts <- attempts+1; hand_back <- attempts >= 3
 27 status <- approved iff all_ok and success_criteria_met
 28 if approved: approved_commit <- HEAD            // R14: ceiling of the diff
\end{lstlisting}

\paragraph{The adversarial judge.} Listing~\ref{alg:judge} is the
claim-based verification model of Section~\ref{sec:design}: it treats the
task file as a collection of claims, confronts them with the repository,
and returns a verdict. The baseline handling is adversarial: the declared
\texttt{base\_commit} must match the Git anchor recorded when the task
started (else \emph{baseline tampering}), and \texttt{approved\_commit},
when present, is the \emph{ceiling} of the diff, so later tasks' changes
do not count as undeclared scope for this one (\texttt{judge.py:1377}).

\begin{lstlisting}[caption=adversarial judge (kata/judge.py).,label=alg:judge]
ALGORITHM judge_task(task_data, cwd, config)
  1  task_data, blind_spots <- normalize(task_data)
  2     // sections that are not maps or files lists with non-maps become
  3     // a confessed blind spot, never an AttributeError (traceback exits 1,
  4     // the same code as REFUTED - indistinguishable to CI readers)
  5  base <- task_data.base_commit; anchor <- git refs/kata/base/<hash(task)>
  6  if anchor exists but differs from base          -> baseline_tampering (high)
  7  if base does not resolve or is not ancestor of HEAD -> baseline_tampering
  8  ceiling <- task_data.approved_commit           // R14
  9  if ceiling present but invalid -> baseline_tampering; else diff <- base..ceiling
 10  diff <- git diff (base..ceil) + synthetic untracked adds; skip ".kata/" bookkeeping
 11  changed <- changed files in the same window
 12  claims <- collect_claims(task_data)   // lint/test/coverage/surgical/intent
 13  unverifiable <- collect_unverifiable_claims(task_data)  // success criterion
 14  re_ran <- {} ; if claims mention checks:
 15      results <- run_all(...)           // re-execution
 16      re_ran <- {check: results[check].ok}
 17  frauds <- baseline_frauds
 18  frauds += hunt_weakened_checks(diff)          // Listing 6
 19  frauds += hunt_false_completion(task_data, re_ran)     // claimed pass, rerun fails
 20  frauds += hunt_scope_creep(task_data, changed)         // changed but not declared
 21  frauds += hunt_unauthorized_action(task_data)          // auth_owed, no AUTH line
 22  frauds += hunt_spec_betrayal(task_data)                // intent.all_agree == false
 23  frauds += hunt_debris(diff, changed)                   // .tmp, scratch, debug prints
 24  blind_spots += unreadable test languages; ignored code files; no claims at all
 25  verdict <- high frauds? REFUTED
 26             : any frauds?       VERIFIED WITH CAVEATS
 27             : blind_spots?      UNVERIFIABLE    // "could not look" never "all clear"
 28             :                   VERIFIED
\end{lstlisting}

\paragraph{Weakened-checks hunt.} Listing~\ref{alg:weakened} is the most
elaborate of the hunters. A weakened check is a test that exists,
runs, and verifies nothing: a body replaced by \texttt{pass}, an assertion
commented out, a new test whose first instruction is a no-op
(\texttt{assert True}, \texttt{pytest.skip}, \texttt{it.skip},
\texttt{t.Skip}, \texttt{XCTSkip}). The hunts are language-aware: probes
for each language (\texttt{judge.py:29--339}) define what a removal, an
empty body, and a no-op look like in that syntax, so a Go pattern is never
applied to a Ruby file. One subtlety deserves emphasis: the
\emph{pair rule}: a removed assertion is only a fraud if no added
line in the same file contains an assertion of the same family, because
changing \texttt{expect(x).toBe(1)} to \texttt{expect(x).toBe(2)} is a
modification, not a removal. Files whose language has no probes are
\emph{confessed} as unreadable, never silently cleared
(\texttt{judge.py:728}).

\begin{lstlisting}[caption=weakened-checks hunt (kata/judge.py).,label=alg:weakened]
ALGORITHM hunt_weakened_checks(diff)
  1  current <- ""; is_new <- false; pending <- []   // removals awaiting decision
  2  for each line in diff:
  3    if line starts with "diff --git":
  4        flush pending into frauds (file:current)   // removals not revoked
  5        current <- file name; is_new <- false
  6    if "new file mode"    then is_new <- true      // new files: empty-body scan later
  7    if "deleted file mode" then skip                // deleting a test is not a weakened one
  8    if not a test file (name/dir convention) or no probes for its language: continue
  9    if is_new: collect '+' lines per file; continue
 10    if line starts with '+':
 11        if an assertion of the family is on this + line:
 12            pending <- []                           // changed value, not removal
 13        for each (pattern, desc) in probes.weakened:
 14            if pattern matches line:
 15                if line starts with '-' and family probes exist:
 16                    pending += (line, desc)         // decide at flush
 17                else: frauds += (weakened_checks, high, desc)
 18                break                               // one fraud per diff line
 19  4  flush pending at end
 20  5  for each new test file: for each empty/no-op body found
 21        (declaration, skipped comments, docstrings, then first meaningful line
 22        is pass/assert True/skip/xit/no-op) -> frauds += weakened_checks (high)
 23  6  return frauds
\end{lstlisting}

\paragraph{Audit grading.} Listing~\ref{alg:audit} grades each phase of a
completed task as followed, skipped, faked, or degraded, and names the
concrete risk each skip or fake created (\texttt{report.py:169}). The faked
pattern is only catchable because there is objective logic behind it: the
audit reads the YAML and detects \texttt{answered: true} with empty
content, or a verify/twins claim without its evidence.

\begin{lstlisting}[caption=audit grading (kata/report.py).,label=alg:audit]
ALGORITHM audit_task(data)
  1  if preflight.skills_missing is non-empty:
  2      grade preflight as degraded (phase ran without its skill)
  3  for phase in {fit, think, intent}:        // content key: reason/problem/code_does
  4      if skipped            -> grade skipped, state the risk
  5      elif not answered     -> not graded (task in progress)
  6      elif content empty    -> grade FAKED, state the risk
  7      else                  -> grade followed
  8  for phase in {simplify, surgical}:        // content key: minimum_code/files
  9      same decision; empty/missing content -> FAKED
 10  verify:  success_criteria_met but no evidence (ruff/tests/coverage false)
 11           -> FAKED ("success affirmed without execution"); evidence -> followed
 12  twins:   defect_fixed but not searched -> FAKED; searched -> followed
 13  return grades + concrete risk per non-followed phase
\end{lstlisting}

\paragraph{Preflight and trap harness.} Listing~\ref{alg:doctor} checks
skill installation per frontend; Listing~\ref{alg:traps} drives the
adversarial trap suite (\texttt{eval/run\_traps.py}): every scenario pairs
a \texttt{fixture/} with a \texttt{ground\_truth.yaml} specifying the
expected verdict and the exact frauds, and the harness fails when the
verdict differs, a fraud is missing, or an unexpected fraud appears. A new
scenario must be shown to fail when its defect is reintroduced, so a
scenario that passes in both states protects nothing.

\begin{lstlisting}[caption=preflight doctor (kata/skills.py).,label=alg:doctor]
ALGORITHM doctor()
  1  for each frontend in {opencode, claude-code}:
  2      expected <- phase skills (+ orchestrator "kata" for claude-code)
  3      installed <- {s in expected : exists(config_dir/skills/s)}
  4                    // a broken symlink does not count: exists() follows links
  5      partial <- some installed and some missing
  6  return per frontend: ausente | parcial | completo
  7  exit 1 iff any frontend is partial
     // absent is fine (CLI works without frontends);
     // partial silently loses a phase of the cycle
\end{lstlisting}

\begin{lstlisting}[caption=trap harness (eval/run\_traps.py).,label=alg:traps]
ALGORITHM run_traps()
  1  for each scenario in eval/scenarios/        // sorted; 24 as executed
  2      in a fresh sandbox (excluding .kata/ from git; one scenario opts
  3        in to the real environment with kata_visivel: true)
  4      repeat gt.judge_runs times in the same workspace   // s23: the
  5          // judge's own run leaves artifacts; run two must not accuse them
  6      run kata --judge inside the fixture          // no access to ground truth
  7      gt <- ground_truth.yaml (expected verdict + exact frauds)
  8      fail if  verdict != gt.expected_verdict
  9          or  any expected fraud missing
 10          or  any unexpected fraud present          // two-sided contract
 11      if gt.expected_audit:
 12          run kata --audit and compare per phase  // grades, e.g. gauntlet
 13  // honest scenarios must return VERIFIED, blind spots UNVERIFIABLE,
 14  // fraud scenarios REFUTED; a scenario that passes with its defect
 15  // reintroduced protects nothing and is rejected
\end{lstlisting}

The listings share one discipline that the reader should verify against
the code: what is executable is executed, and what cannot be executed is
declared. Listing~\ref{alg:fit} fails the gate rather than guess a line
count it could not measure; Listing~\ref{alg:judge} returns UNVERIFIABLE
rather than VERIFIED when it could not observe; the audit grades
\emph{degraded} a phase whose own skill was never loaded. Every placeholder
in these descriptions is a decision that the code makes explicitly, and
each such decision is covered by a unit test in \texttt{tests/}.

\subsection{Changes in version 0.8.0}
\label{sec:release-080}

The evaluation in this paper was run against the code identified in the
Declarations as the evaluated version. The current release, 0.8.0, is not
that code: it keeps the nine-phase cycle and the verdict model, and changes
the evidence it records and the edges it checks. The additions are:

\begin{itemize}
\item \textbf{A fourth verification role.} A project may declare
  \texttt{verify.typecheck}; it runs between lint and test and is judged by
  its exit code. It has no default, and \texttt{verify.typecheck\_clean}
  stays \texttt{null} when the role is undeclared, because no universal type
  checker exists and a role that did not run must not be recorded as passed.
\item \textbf{Execution evidence.} VERIFY stamps \texttt{kata\_version},
  \texttt{gate\_used}, \texttt{commands} (role $\rightarrow$ command), and
  \texttt{ran\_at} in the task file; the report prints them, and the JUDGE
  compares them with its own run, adding a caveat when the version, the gate,
  or a command differs from the recorded one.
\item \textbf{A closed diff window.} \texttt{approved\_commit} is not
  recorded while \texttt{HEAD} is still the baseline, because a ceiling equal
  to the floor is an empty diff window. \texttt{kata --stamp TASK
  [--commit SHA]} records the commit that ends the task, validating that it
  resolves, descends from \texttt{base\_commit}, and is an ancestor of
  \texttt{HEAD}.
\item \textbf{An eighth fraud category.} \texttt{hunt\_triviality\_claim}
  flags \texttt{fit.trivial=true} with no declared files when the measured
  diff exceeds a deliberately gross tolerance (100 added lines or ten files).
  The three-file honest task of s16 remains \texttt{VERIFIED}, because the
  tolerance is set to catch a sixteen-thousand-line change approved as
  trivial, not a small helper change.
\item \textbf{A finer false-completion rule.} A check that did not run
  because the environment lacks the tool is a confessed blind spot, not a
  false completion: ``I could not run it'' is not ``I ran it and it failed''.
\item \textbf{Attribution inside the window.} Commits that fall between
  \texttt{base\_commit} and \texttt{approved\_commit} are attributed to
  sibling tasks by the stamps the repository already holds: a commit stamped
  by an approved sibling leaves the window with a caveat naming the commit
  and the task, and an unstamped commit makes the verdict
  \texttt{UNVERIFIABLE} rather than accusing honest work or blessing it.
\item \textbf{Stricter configuration and diagnosis.} Unknown keys at any
  level of \texttt{.kata/config.yaml} are named errors; shell operators in a
  declared command are refused; \texttt{kata --doctor} reports skills
  installed by a different Kata version; and a path flag ignored because its
  role is declared is reported instead of silently discarded.
\end{itemize}

These changes are covered by the unit suite and by the current trap suite of
25 scenarios (s20--s25 were added after the evaluation, together with the
fixes they guard). They do not alter the 19-scenario results reported in
Section~\ref{sec:impact}, and we did not re-run the evaluation on 0.8.0; the
Declarations state which commit produced each number.

\section{The development cycle in action}
\label{sec:cycle}

To demonstrate the cycle, we applied Kata to a real bug fix in a small
example project: a calculator whose \texttt{dividir} (divide) function raised
an unhandled \texttt{ZeroDivisionError}. The change adds a
\texttt{ValueError} guard and a regression test. The working tree contains
two modified files (11 changed lines), so the FIT gate classifies the task
as non-trivial and routes it to the full cycle.

\subsection{FIT --- task classification}

The FIT phase measures the real diff and classifies the task; its
control flow is Figure~\ref{fig:fit}.

\begin{lstlisting}
  diff: 2 file(s), 11 changed line(s)
  -> non-trivial task

  Available routes:
    [1] code-loop   — full cycle
    [2] plan-first  — planning only
    [3] question    — diagnosis only
    [4] research    — needs research before acting
    [5] inference   — based on inference only

  Chosen route [1]: 1
  Brief justification (optional): fix division by zero without a guard
\end{lstlisting}

A trivial task (at most one file, fewer than ten lines) would skip the
planning phases and go directly to VERIFY --- the triviality gate of the
Fable Method. In the evaluated version, and still in 0.8.0, the measured diff
counts untracked \texttt{.kata/*.yaml} files (the task file itself and the
project configuration), so in a project that does not ignore \texttt{.kata/}
a one-line change is no longer trivial: one file becomes two files and three
lines in our reproduction on 0.8.0. The JUDGE and the SURGICAL file list
filter this bookkeeping, but \texttt{fit.diff\_stats} does not; the trap
harness hides the defect because it git-excludes \texttt{.kata/} in every
fixture. No trap scenario covers it. This is a
defect of the current release, not a historical note: a reader who relies on
the triviality gate should ignore \texttt{.kata/} in the project or accept
that a one-line change may take the full cycle.\footnote{The \texttt{kata} CLI reports in Portuguese; the
CLI outputs quoted in this paper are translated into English for
presentation. Recurring terms: \emph{não-trivial} = non-trivial;
\emph{rota escolhida} = chosen route; \emph{arquivo(s)} = file(s);
\emph{linha(s)} = line(s); \emph{limpo} = clean; \emph{passou} = passed;
\emph{critério de sucesso} = success criterion; \emph{veredito} = verdict;
\emph{fraude(s)} = fraud(s); \emph{re-execução} = re-execution;
\emph{ocorrência(s)} = occurrence(s).}

\subsection{THINK --- declaring before the evidence}

THINK records the problem, assumptions, alternatives, unknowns, and the done
criterion \emph{before} the evidence exists (Figure~\ref{fig:think}):

\begin{lstlisting}
  What is the exact problem I am solving?
    the dividir (divide) function raises ZeroDivisionError with no guard
  What assumptions am I making? (semicolon-separated)
    none; API is stable
  What alternatives did I consider? (semicolon-separated)
    guard with ValueError; return None
  What do I NOT know? (do I need to ask first?) nothing
  What is 'done'? (success criterion + how I will verify it)
    test test_dividir_por_zero passes and coverage >= 70%
\end{lstlisting}

The done criterion is declared before the evidence exists (Fable Step 1).
VERIFY will confront this declared criterion with the final result --- not
ask ``is it satisfied?'' to a criterion that only exists afterwards.

  src/calculadora.py — necessary for this task? [Y/n]: y
  tests/test_calculadora.py — necessary for this task? [Y/n]: y
  Are the removed imports only those your change made unused? [Y/n]: y
\end{lstlisting}

\subsection{VERIFY --- objective verification}

VERIFY runs the objective checks in order: lint, test, coverage against the
gate, and the success criterion confronted with the done criterion declared
in THINK (Figure~\ref{fig:verify}):

\begin{lstlisting}
[>] ruff check src/ tests/
  [ok] clean

[>] pytest tests/ --tb=short -q
  [ok] passed

[>] coverage (gate >= 70%)
  [ok] passed (100.0%)

[>] Success criterion of the task
  (declared in THINK: test test_dividir_por_zero passes and coverage >= 70%)
  Is the success criterion of the task satisfied? [Y/n]: y

  [!] approved_commit not recorded: HEAD is still base_commit
      After the commit, run `kata --stamp fix-division-by-zero`

  [ok]  KATA CYCLE — APPROVED
\end{lstlisting}

Each role runs the command declared in
\texttt{.kata/config.yaml} for that role, or the Python default (ruff,
pytest, pytest-cov with \texttt{--cov-fail-under}) when the role is not
declared; \texttt{typecheck} is the exception with no default, and it only
runs when declared. Coverage is short-circuited when the test step fails. A
task is approved only when all checks and the success criterion pass. In
0.8.0 the VERIFY also records the execution evidence --- the version, the
gate, the commands, and the timestamp --- and, when the approval happens
before the commit, warns that \texttt{approved\_commit} is not stamped and
prints the \texttt{--stamp} command that closes the JUDGE's window.

\subsection{TWIN CHECK --- searching for recurring patterns}

TWIN CHECK (Figure~\ref{fig:twin}) runs after VERIFY and only for an
approved task. When a defect has been fixed, the same pattern often exists
elsewhere. If the INTENT gate
recorded a disagreement (\texttt{all\_agree: false}), TWIN CHECK
automatically infers that a bug was resolved; otherwise, it asks the user
whether one was. When confirmed, it searches the project for the pattern
and records the answer:

\begin{lstlisting}
  Was a defect fixed? Search for a similar pattern? [y/N]: y

  Pattern to search (regex): a / b
  Searching for 'a / b' in the project...
  [ok] Found in 1 file(s):
     ./src/calculadora.py:7  return a / b
  Fix the remaining occurrences now? [y/N]: n
\end{lstlisting}

Recording a negative answer distinguishes ``no defect'' from ``not
checked'', which is the point of asking.

\subsection{The task file}

The entire cycle is persisted in a task file (\texttt{.kata/<task>.yaml}),
so the evidence behind an approval is persistent and auditable, not
conversational. The file records the done criterion, the FIT classification,
the THINK declarations, the SIMPLIFY/INTENT/SURGICAL answers, the VERIFY
results (including the coverage percentage and the attempt counter), the
TWIN CHECK result, and the artifact checks. It also records
\texttt{kata\_version} and, in the verify block, \texttt{gate\_used},
\texttt{commands}, and \texttt{ran\_at}, so the JUDGE can tell whether the
version, the gate, or the command it re-runs is the one that produced the
evidence. \texttt{base\_commit} (the HEAD captured when the task started) and
\texttt{approved\_commit} (the commit that ends the task) define the diff
window, which allows the JUDGE to diff \texttt{base..approved} even after
the task has been committed --- changes made by later tasks do not count as
undeclared scope for this one. \texttt{approved\_commit} is not written while
HEAD is still the baseline; the commit is stamped afterwards with
\texttt{kata --stamp}.

The task file from the demonstration of Section~\ref{sec:cycle} is shown
in Listing~\ref{lst:taskfile}. Note the structure: every phase has an
\texttt{answered} flag (true when a human answered, false when filled with
defaults) and a \texttt{skipped} flag (true only in non-interactive mode).
The audit mode reads these flags to distinguish followed, skipped, and
faked phases. The \texttt{verify} section records the attempt counter and
the hand-back flag, which implement the hard bound of Fable Step 5. The
\texttt{twins} section records whether a defect was fixed and whether a
pattern search was performed --- recording a negative answer is what

\section{The adversarial layer: JUDGE}
\label{sec:judge}

The JUDGE is the phase that no skill can perform (Figure~\ref{fig:judge}). It treats the task file as
a collection of claims and confronts them with the repository. It re-runs
the claimed checks, diffs the claims against the actual changes, and hunts
eight fraud categories:

\begin{itemize}
\item \textbf{weakened checks}: a test whose body was replaced by
\texttt{pass}, an assertion turned into a comment, or a new test whose body
is only \texttt{assert True} --- it exists, it runs, it verifies nothing;
\item \textbf{false completion}: the report claims lint clean, tests
passing, and coverage at the gate, but the re-execution fails. In 0.8.0 a
command that could not run because the environment lacks the tool is a
confessed blind spot, not a false completion: ``could not run'' is not
``ran and failed'';
\item \textbf{scope creep}: the report declares one file, the tree has
four;
\item \textbf{unauthorized action}: an irreversible action was taken without
a documented AUTH line;
\item \textbf{specification betrayal}: the intent gate recorded a
disagreement and the task was approved anyway. In the evaluated version this
also caught disagreements the gate had resolved and recorded --- the normal
record of a bug fix, whose honest completion came back \texttt{REFUTED}, as it
did in six in-session runs of the external study
(Section~\ref{sec:external-evaluation}). Since
commit \texttt{15ccb7a}, a recorded \texttt{conflict\_resolution} is accepted
without verification and only an unresolved disagreement is betrayal; a
twenty-first trap scenario (s21) covers the resolved case;
\item \textbf{debris}: temporary files in the diff;
\item \textbf{baseline tampering}: the \texttt{base\_commit} declared in
the YAML diverges from the Git anchor recorded when the task started;
\item \textbf{triviality claim}: \texttt{fit.trivial=true} with no declared
files, when the measured diff exceeds a gross tolerance (100 added lines or
ten files). Without it, a sixteen-thousand-line change approved as trivial
would pass because the triviality flag itself disables the scope hunt. The
category was added in 0.8.0 and was not part of the evaluated seven.
\end{itemize}

Two further checks in 0.8.0 refine the window rather than add categories.
The JUDGE compares the recorded version, gate, and commands with the ones it
re-runs and adds a caveat when they differ, because a verdict produced under
another gate or another command is not the same verdict. And it attributes
the commits inside a closed window to sibling tasks by their
\texttt{approved\_commit} stamps: a commit stamped by an approved sibling
leaves the window with a caveat naming the commit and the task, while an
unstamped commit makes the verdict \texttt{UNVERIFIABLE} instead of accusing
honest work or blessing it.

These guarantees hold against claims that re-execution or the diff can
contradict; they do not hold against an agent that also controls Git
metadata or the execution environment. Section~\ref{sec:threat-model} states
that boundary explicitly and reproduces two live bypasses --- rewriting the
baseline anchor and emptying the diff window --- that yield a VERIFIED
verdict on a weakened test as evaluated; a reader relying on the JUDGE as a
merge gate should read that boundary before the results below.

Frauds are graded by severity: weakened checks, false completion,
unauthorized actions, specification betrayal, and baseline tampering are
\emph{high-severity}; scope creep is \emph{medium-severity} (when
undeclared files number two or fewer) or \emph{high-severity} (when three or
more); a triviality claim is \emph{medium-severity} below 1{,}000 added lines
and 50 files, and \emph{high-severity} at or above either; and debris is
\emph{low-severity}. Verdict calculation follows
strictly (Listing~\ref{alg:judge}): any high-severity fraud produces a
\texttt{REFUTED} verdict; medium- and low-severity findings yield
\texttt{VERIFIED WITH CAVEATS}; confessed blind spots without fraud result
in \texttt{UNVERIFIABLE}; and an entirely clean review with all re-executions
passing returns \texttt{VERIFIED}.

\subsection{Honest work: VERIFIED}

After committing the task of Section~\ref{sec:cycle}, we ran
\texttt{kata --task fix-division-by-zero --judge}. The judge re-executed
the claimed checks and returned:

\begin{lstlisting}
[ok]  VERDICT: VERIFIED

  Verified claims:
    • ruff check clean (no lint errors)
    • all tests pass
    • coverage >= gate (100.0%)
    • 2 file(s) changed surgically (necessary)
    • intent aligned: code, test, and spec agree

  Claims accepted without verification (not re-executable):
    • success criterion satisfied

  Re-execution:
    [ok] lint
    [ok] test
    [ok] coverage
\end{lstlisting}

Note that the success criterion is listed as \emph{accepted without
verification}: it is a subjective confirmation the user gives during VERIFY,
and no command reproduces it. Presenting it as verified would be the
fraud the judge exists to hunt. This task was approved before its change was
committed. In the evaluated version, \texttt{base\_commit} and
\texttt{approved\_commit} coincided, so the diff window was empty and the
surgical and weakened-check claims were not confronted with a diff
(Section~\ref{sec:threat-model}). In 0.8.0 the cycle no longer records
\texttt{approved\_commit} while \texttt{HEAD} is still the baseline
(Listing~\ref{lst:taskfile} shows it absent), and the JUDGE diffs the working
tree; after the commit, \texttt{kata --stamp} records the commit that ends the
task and closes the window.

\subsection{Fraudulent work: REFUTED}

We then ran the judge against a trap scenario from the evaluation suite: a
``completed'' task whose report claims ruff clean, tests passing, and
coverage at the gate, but where the re-execution fails all three (an unused
import in the source, a failing test, and coverage skipped because pytest
failed):

\subsection{Blind spots are confessed}

The judge also confesses its blind spots. If it could not observe something
--- a test language it has no probes for (it knows Python, JS/TS, Go, Ruby,
Rust, Java/Kotlin, C\#, PHP, and Swift), a file outside Git's diff, a
baseline that no longer resolves --- the verdict is UNVERIFIABLE, never
VERIFIED. ``I could not look'' is never reported as ``all clear''. With
fraud present, the fraud decides the verdict and the blind spots are still
listed.

\subsection{Threat model}
\label{sec:threat-model}

The JUDGE is adversarial toward the claims in a task file, not toward an
agent that controls the repository. We state the threat model explicitly,
because the difference matters to anyone who uses the JUDGE as a merge gate.

\textbf{Adversary.} A coding agent that writes both the code and the task
file, runs shell commands, and can write to the working tree and to the local
Git repository, including its refs and \texttt{.git/info/exclude}. It wants a
passing exit code for work that does not meet its claims.

\textbf{In scope.} Claims that re-execution or the Git diff contradict:
checks declared as passing that fail, changed files that were not declared,
the planted patterns of Section~\ref{sec:self-check}, and a
\texttt{base\_commit} edited in the YAML after the anchor was recorded (s14).

\textbf{Out of scope, with reproduced evasions.} Tampering with Git metadata,
with the environment the checks run in, or with the machine that runs the
JUDGE, and content that is plausible but false. We reproduced the evasions
below against \texttt{kata/judge.py} as evaluated (unchanged since commit
\texttt{230e81a}), in a temporary repository whose task replaces a test body
with \texttt{pass}. Without evasion, the JUDGE returns REFUTED for weakened
checks.

\begin{itemize}
\item \textbf{Rewriting the anchor.} The anchor
\texttt{refs/kata/base/<sha256(task)>} is an ordinary ref in the repository
the agent controls (\texttt{record\_baseline\_ref}, \texttt{judge.py:465}).
Editing \texttt{base\_commit} alone is caught as baseline tampering, but
moving both the YAML and the ref to the final commit with
\texttt{git update-ref} empties the diff window, and the verdict is VERIFIED
(exit 0). Deleting the ref and editing the YAML yields UNVERIFIABLE (exit 0).
After the evaluated version, commit \texttt{3454fc7} (shipped in 0.8.0) narrowed this path: the
anchor is now written with a reflog, and an anchor that has pointed at more
than one commit is reported as baseline tampering (trap scenario s22).
Deleting and recreating the anchor erases its reflog and still evades that
check locally; \texttt{kata --judge --trusted-base <ref>} closes it in CI by
taking the diff floor from the merge base with a ref the agent cannot move,
which protects only as far as that ref is protected on the remote.
\item \textbf{Empty diff window.} The ceiling check (\texttt{judge.py:1424})
accepts an \texttt{approved\_commit} equal to \texttt{base\_commit}, because
Git counts a commit as its own ancestor. The weakened test is then invisible
and the verdict is VERIFIED (exit 0), whether or not the change has been
committed. No tampering is needed: the cycle records \texttt{approved\_commit}
as the HEAD at approval (\texttt{cli.py:902}), so a task approved before its
change is committed produces exactly this window. In the evaluated version,
the demonstration task of Listing~\ref{lst:taskfile} was such a case, and
the suite did not exercise it: s17 records an \texttt{approved\_commit} later
than the baseline. s20 now covers it. This path was fixed after the evaluated
version, in commit \texttt{3cacc5a} (shipped in 0.8.0): when
\texttt{approved\_commit} equals \texttt{base\_commit} and \texttt{HEAD} is
still there, the JUDGE diffs the working tree; when \texttt{HEAD} has moved
on, it confesses the empty window as a blind spot and can no longer return
VERIFIED (UNVERIFIABLE when no fraud is found); and the cycle no longer
records \texttt{approved\_commit} while \texttt{HEAD} is still the baseline.
Regression tests and a twentieth trap scenario (s20) cover the fix. The
workflow that closes the window after the commit is \texttt{kata --stamp
TASK}: it records the commit that ends the task after validating that it
descends from the baseline and is an ancestor of \texttt{HEAD}. The fix does
not close the anchor rewrite above, which we re-ran against it and
which still yielded VERIFIED at that commit.
\item \textbf{Manufacturing a blind spot.} UNVERIFIABLE exits 0 by design
(\texttt{cli.py:1649}), a fail-open policy chosen so that projects in
unprobed languages are not failed wholesale. An agent can exploit it: a
weakened test hidden with \texttt{.git/info/exclude} (s19) or written in an
unprobed language (s12) yields UNVERIFIABLE and passes a gate that reads only
the exit code.
\item \textbf{Declaring everything.} Scope creep compares the diff with the
declared files, and \texttt{necessary: true} is self-reported: an agent that
declares every file it touched is never charged with scope creep, however
unnecessary the change.
\item \textbf{Plausible but false content.} The audit grades a phase as faked
when it is marked answered with empty or default content
(\texttt{\_audit\_task}, \texttt{report.py:169}); a phase filled with
plausible but false content is graded followed. \texttt{conflict\_resolution} is self-reported: accepted unverified, any non-empty
text, one line, disarms spec betrayal, a high-severity fraud
(commit \texttt{15ccb7a}).
\end{itemize}

These paths bound what a verdict means: VERIFIED says that the claims
survived the checks the JUDGE could run over the diff window it was given,
not that an agent with repository access could not have arranged that
window. Detecting a deleted and recreated anchor without a trusted base, a
fail-closed option for UNVERIFIABLE, and an evaluation against an
adaptive adversary instructed to evade the JUDGE are future work.

\subsection{Audit grades and concrete risks}

The audit mode (\texttt{kata --audit}) grades each phase of a task as
followed, skipped, faked, or degraded, and names the concrete risk each
skip or fake created. Table~\ref{tab:grades} summarizes the four grades
and what each one means for the trustworthiness of the task.

The faked pattern is a phase
marked as answered without real content. This is only possible because

the audit reads the YAML and detects \texttt{answered: true} with empty

but false content (Section~\ref{sec:threat-model}).

\end{lstlisting}

The audit is Kata's equivalent of the Fable Method's audit, and it
catches phases that were filled in without being observed.

\subsection{Preflight and installation checking}

The orchestrator is not self-contained: at each phase it loads the matching
skill and follows its instructions. When a skill is not installed, the call
fails, the orchestrator has no instructions for that phase, and the model
improvises from the phase name. The result is a task file with the section
filled in and nothing behind it --- the faked phase the audit
exists to catch, except produced by the tooling rather than by the agent,
and invisible in the output.

The \texttt{kata --doctor} command reports, per frontend, which of the
expected skills are present under the host's configuration directory. A
broken symlink does not count as installed, because \texttt{exists()}
follows the link and so does the host when it tries to load the skill. A
partial install is what fails, not an absent one: exit code 1 is reserved
for a frontend that has some skills but not all, because someone with 9 of
the 10 phase skills runs the whole cycle and silently loses a phase. With
no frontend installed at all, \texttt{--doctor} says so and exits 0 --- the
CLI works without any. Domain adapters are optional and never fail
\texttt{--doctor}: missing domain adapters (such as \texttt{kata-devops} or
\texttt{kata-data-analysis}) are reported as hints because a coding task
does not need them.

When a skill fails to load mid-cycle, the orchestrator is instructed not
to improvise: it falls back to a per-phase minimum contract documented in
the orchestrator itself, records the skill name in
\texttt{preflight.skills\_missing}, and discloses it in the report. The
audit grades such a phase as degraded, not followed, because whatever the
other grades read was written without those instructions. VERIFY and JUDGE
degrade best, because their logic lives in the Python package rather than
in the skill text. Since 0.8.0, \texttt{--doctor} also reads the version
stored in each \texttt{.kata-managed} marker and warns when the installed
skills were written by a different Kata version than the one running: a copy
of 0.7.4 under a 0.8.0 CLI would otherwise report ``complete installation''
while the agent followed phase instructions from the older release. This is
a warning, not a failure, because a pinned installation may be intentional;
exit code 1 remains reserved for a partial install.

\section{Using the kata CLI}
\label{sec:usage}

This section documents how to install Kata and use its command-line
interface, so that the demonstrations of
Sections~\ref{sec:cycle}--\ref{sec:audit} can be reproduced. Kata is
published on the Python Package Index (PyPI) as \texttt{kata-dev} (the
command stays \texttt{kata}); the installable package version is
\texttt{0.8.0}. The package, the release tag \texttt{v0.8.0} and the code
that was measured are three different revisions, and the Declarations
(Section~\ref{sec:declarations}) define them once, together with the term
``evaluated version'' used throughout this paper. A DOI will
be minted upon acceptance and inserted in the camera-ready version. The
canonical user documentation is the README (which ships as the package's long
description on PyPI) and \texttt{DOCUMENTATION.md} (versioned in the
repository, not in the wheel). Both are versioned with the source; the
Declarations section gives the exact commits and reproduction commands,
together with the comparison and external-study harnesses and the
measurement and audit tooling cited in Sections~\ref{sec:design} and
\ref{sec:external-evaluation}.

\subsection{Installation}

Kata requires Python 3.11 or newer. The recommended installation path is
the published package, isolated in its own environment with
\texttt{pipx} or \texttt{uv} so it does not touch the current one:

\begin{lstlisting}
pipx install kata-dev
# or: uv tool install kata-dev
kata --install all       # opencode + claude-code (copies the bundled skills)
kata --doctor            # checks the installation
\end{lstlisting}

Development on the source checkout instead installs the package in
editable mode, with the \texttt{dev} extra bringing the lint, test, and
coverage tools the CLI itself executes:

\begin{lstlisting}
pip install -e '.[dev]'
\end{lstlisting}

To run the CLI once without installing it permanently (CI/headless
friendly), \texttt{pipx} or \texttt{uv} can run it directly from the
package:

\begin{lstlisting}
pipx run kata-dev --version
uv tool run --from kata-dev kata --version
\end{lstlisting}

The agent frontends are installed separately through symlinks. \texttt{make
install} links the OpenCode agent and skills into the OpenCode
configuration directory (honoring \texttt{OPENCODE\_CONFIG\_DIR}, defaulting
to \texttt{\~{}/.config/opencode}); \texttt{make install-claude-code} links
the skills into the Claude Code configuration directory (honoring
\texttt{CLAUDE\_CONFIG\_DIR}, defaulting to \texttt{\~{}/.claude}).
Because the installer creates symlinks, rebuilding the generated frontends
with \texttt{make build-skills} is immediately visible without
reinstalling. \texttt{kata --install} performs the same installation as a
copy from the wheel's bundled assets, so a reader without the checkout can
install; it adopts a symlink created by the checkout installer when the
target has the same content, and \texttt{kata --doctor} names the mode
(link, copy, or mixed) and warns when the installed skills were written by a
different Kata version.

a command containing a shell operator is refused because commands run
without a shell.

\subsection{Typical workflow and exit codes}

In practice, Kata integrates into software engineering workflows along two
distinct patterns: interactive authoring and automated gating.

\paragraph{Interactive authoring workflow.} A developer or coding agent
follows three sequential CLI commands:
\begin{enumerate}
\item \textbf{Initialize}: \texttt{kata --init fix-login} measures the working diff,
prompts for the task route (Phase 0: FIT), records the problem, assumptions,
and declared done criterion (Phase 1: THINK), captures the starting HEAD as
\texttt{base\_commit}, and creates an independent Git anchor at
\texttt{refs/kata/base/<sha256(task)>}.
\item \textbf{Execute and verify}: \texttt{kata --task fix-login} guides the
change through SIMPLIFY (checking minimality), INTENT (aligning code, test,
and spec), SURGICAL (auditing declared files), VERIFY (running lint, declared
typecheck, tests, and coverage against exit codes), and TWIN CHECK (searching
project-wide for defect recurrence). Upon approval it records the execution
evidence; \texttt{approved\_commit} is not written while HEAD is still the
baseline, so the commit that ends the task is stamped next with
\texttt{kata --stamp fix-login}, which sets the diff ceiling.
\item \textbf{Adversarial review}: \texttt{kata --task fix-login --judge}
re-executes all claimed checks, diffs the Git baseline against the approved
ceiling, and hunts for the eight categories of fraud before merge.
\end{enumerate}

\paragraph{Automated CI and review pipelines.} In automated pipelines,
Kata operates non-interactively without prompting:
\begin{itemize}
\item \textbf{Per-commit CI}: \texttt{kata --check-only} executes the declared
or default lint, test, and coverage commands, returning exit code 0 if all
pass or 1 if any fails.
\item \textbf{Pull request gating}: \texttt{kata --task <name> --judge}
re-runs checks and hunts frauds against the PR's baseline anchor;
\texttt{kata --task <name> --judge --trusted-base <ref>} closes a recreated
anchor with a CI-only ref the agent cannot move, not locally;
\texttt{kata --task <name> --audit} ensures no phase was faked or silently
skipped in headless mode.
\end{itemize}

Exit codes make the CLI directly composable in shell scripts and CI
pipelines:
\begin{itemize}
\item \textbf{0}: The requested operation passed (an approved cycle, a
\texttt{VERIFIED} or \texttt{VERIFIED WITH CAVEATS} judge verdict, a clean
audit, or an \texttt{UNVERIFIABLE} blind spot confession). In particular,
\texttt{VERIFIED WITH CAVEATS} and \texttt{UNVERIFIABLE} exit 0: the judge
verified what it could and approved with notes, or found no fraud but could
observe nothing --- treating either as failure would equate an honest
limitation with high-severity fraud. This makes UNVERIFIABLE fail-open: an
agent can manufacture a blind spot, so a CI job that must fail on anything
short of VERIFIED has to read the verdict rather than the exit code
(Section~\ref{sec:threat-model}).
\item \textbf{1}: Failure (a rejected cycle, a \texttt{REFUTED} judge
verdict, an audit with any phase graded \texttt{faked}, \texttt{skipped}, or
\texttt{degraded}, or a partial frontend skill installation).
\item \textbf{2}: Invalid CLI arguments or syntax.
\end{itemize}

\section{Research impact and evaluation}
\label{sec:impact}

Kata is dogfooded: its own lint, tests, and coverage are measured (gate
70\%), and the continuous integration runs the Makefile rather than
restating the commands, so what is verified locally and remotely cannot
drift apart.

Evaluation proceeds in two layers. The first is a \emph{self-check}: 19
adversarial trap scenarios (\texttt{eval/run\_traps.py}, whose driving
logic is Listing~\ref{alg:traps}) plant frauds the
JUDGE must catch and honest work it must not accuse. The second layer is
\emph{external}: 12 bug-fix tasks from public repositories, fixed by two agent
models with and without Kata, with the JUDGE reviewing every final
artifact. The layers answer different questions: the traps measure the
two-sided contract of the JUDGE on fixtures we built ourselves, while the
external study measures what real agent sessions produce on code we did
not write. The first layer answers RQ1 and, reused as the workload of
Section~\ref{sec:exec-comparison}, RQ2; the second answers RQ3. The
exploratory loop study is in Appendix~\ref{sec:gauntlet-pilot}.

\subsection{Self-check: the adversarial trap suite}

catch, and honest scenarios it must not accuse. The trap suite is
deliberately asymmetric in its coverage. Table~\ref{tab:traps} summarizes

Twelve scenarios plant a fraud that must be detected, spanning all seven
fraud categories: weakened checks (a test whose body was replaced by
\texttt{pass} among real tests; an assertion turned into a comment; a new
test whose body is only \texttt{assert True}; a fraudulent test left
outside the index, invisible to \texttt{git diff}; a test body turned into
\texttt{pass \# comment}), false completion (a report claiming lint clean,
tests passing, and coverage at the gate, where re-execution fails all
three), scope creep (a report declaring one file when the tree has four),
unauthorized action (an irreversible action without an AUTH line),
specification betrayal (an intent gate that recorded disagreement and was
approved anyway), debris (real temporary files in the diff), and baseline
tampering (a \texttt{base\_commit} rewritten after the Git anchor was
recorded).

The debris scenario (s06) is the clearest case: it plants real debris beside
files whose names merely look like debris (\texttt{templates/},
\texttt{temperature.py}, \texttt{attempt\_parser.py}), so a judge that
matches the substring ``temp'' would accuse honest work while a judge that
stays silent would clear fraudulent work.

Four scenarios are entirely honest tasks that must come back VERIFIED.
These are as important as the fraud scenarios: a judge that refuses
legitimate work is as broken as one that misses fraud, and unit tests are
poor at catching false positives because they test what we thought
to test. One honest scenario exercises the
triviality gate with three small files and an empty surgical list, where a
naive scope-creep rule would falsely accuse the task. Another exercises
the \texttt{approved\_commit} mechanism end to end: a later task touches
an undeclared file after the approval, and the judge must not count it as
scope creep for the earlier task. The remaining three scenarios expect
UNVERIFIABLE for confessed blind spots: a test in a language the judge has
no probes for (Elixir \texttt{.exs}), a task that claims no
reproducible check at all, and a test hidden from Git via a local ignore
rule that the judge cannot see in the diff.

The trap suite also guards the evaluation harness itself. One scenario
opts into the real environment with \texttt{kata\_visivel: true}: the
harness excludes \texttt{.kata/} from Git in every fixture, and the judge
counting the task's own file as scope creep went unnoticed through ten
review rounds before that scenario existed --- including in the
honest-work scenario whose whole job is catching false positives. The same
rule applies to every fixture added since: reintroducing the defect it was
built for must make it fail, or the scenario is decoration.

and distributed as the \texttt{kata-dev} package on PyPI, installable in
both agent hosts with \texttt{kata --install} (see the Declarations

\subsection{Executed comparison with related gates}
\label{sec:exec-comparison}

The JSERD guidelines for software articles state that ``Software articles
should describe a tool likely to be of broad utility that represents a
significant advance over previously published software (usually demonstrated
by direct comparison with available related software)''.\footnote{JSERD
submission guidelines,
\url{https://journals-sol.sbc.org.br/index.php/jserd/about/submissions},
accessed 2026-09-11. The quoted text is verbatim from the ``Software''
article type description as of the access date.} This
section answers that request by direct comparison: four gates --- Kata, nova, claude-wizard,
and a prompt-only baseline --- reviewed the same 19 adversarial scenarios of
Section~\ref{sec:self-check}, and we measured fraud detection, false positives,
and wall-clock time.

\subsubsection{Protocol}

The comparison reuses the trap suite of Section~\ref{sec:self-check} as the
workload: each scenario is a git repository holding a ``completed'' task
whose task file records the claims the scenario exercises --- lint, tests,
and coverage in the false-completion case, a subset elsewhere (the blind
spots claim no reproducible check at all). The ground truth is
the scenario's \texttt{ground\_truth.yaml}: the expected verdict and the
exact frauds the review must find. Eleven scenarios expect REFUTED; the
other eight expect VERIFIED (s07, s15, s16, s17), VERIFIED WITH CAVEATS
(s06, the debris scenario, whose ground truth expects the three real debris
findings), or UNVERIFIABLE (s12, s13, s19).

Each gate reviews every scenario in a fresh sandbox, without access to the
ground truth. Kata runs its \texttt{--judge} mode. nova and claude-wizard
run headless through the Claude Code CLI (\texttt{claude -p} with
permission bypass), each receiving an identical canonical prompt that
states the review task and the seven fraud categories of the evaluated
taxonomy, prefixed with an
instruction to follow the gate's workflow. The prompt-only baseline receives
the same prompt without any gate-framework instruction; it is a reviewer
with the same information and tool access, not a no-verification condition.
The agent gates report their
verdict as a single JSON object (\texttt{fraud\_detected},
\texttt{fraud\_types}, \texttt{reason}); the harness parses it with a
tolerant JSON decoder. The Kata arm is classified by exact verdict match
against the ground truth; for the agent arms, a scenario is \emph{detected}
when the gate reports the fraud matching the ground-truth types and a
\emph{false positive} when it accuses a scenario whose ground truth expects
no fraud. The debris scenario is the exception to the accusation rule: its
ground truth expects the real debris to be found, so reporting debris
without naming one of the look-alike files counts as correct, while naming
a look-alike counts as a false positive. The \emph{Correct} column counts
the scenarios a gate classified as detected or clean.

of false accusations was measured on scenarios built around its own
conventions.

A fifth, deterministic baseline (run \texttt{make test} and grep the diff
for test-smell patterns: \texttt{pass} bodies, \texttt{assert True}
additions, \texttt{pytest.skip}) sits below all agent gates on detection:
9/11 REFUTED, missing s08 (fraud in an untracked file invisible to
\texttt{git diff --cached}) and s14 (metadata fraud in the YAML
\texttt{base\_commit} field). It also produces two false positives (s06
debris, s07 honest work flagged by smell-pattern matches). The comparison
is diagnostic: test-smell grep catches the syntactic weakening patterns
the JUDGE was designed for (Section~\ref{sec:judge}), but cannot inspect
Git state, track file scope across commits, or distinguish legitimate from
fraudulent \texttt{pass} bodies --- the operations that require
the deterministic code path the paper argues for.

The comparison is subject to important methodological caveats that we state explicitly.
The 19 scenarios and the underlying fraud taxonomy were developed iteratively alongside Kata to serve as regression fixtures. Consequently, the test workloads are strictly in-distribution for Kata --- which includes dedicated architectural mechanisms for these specific boundary conditions --- and out-of-distribution for the alternative gates. The false positives incurred by the agent gates were concentrated on scenarios exercising these repository-level conventions (e.g., \texttt{approved\_commit} diff ceiling on s17, Git local excludes on s19, and missing language probes on s12). Hence, the false positive metric reflects familiarity with these architectural conventions and the presence of direct repository query tools as much as generic reviewer restraint.

The tools were also evaluated in a constrained, emulated configuration: \texttt{nova} and \texttt{claude-wizard} were invoked as structured review prompts within a single headless Claude Code CLI session (\texttt{claude -p}), rather than within their native end-to-end interactive developer workflows. For instance, \texttt{nova} provides a full Model Context Protocol (MCP) server with specialized subagents that was not wired into this isolated review harness, which was scoped to measure a standalone, single-turn change review pass. The agent gates also operated through a single underlying LLM, Claude Code's default model. The harness did not record which model that was; the local Claude Code session logs of the final run's 57 agent reviews, which are not archived in the repository, show \texttt{claude-sonnet-5} through Claude Code CLI 2.1.268. This means their false positives and heuristic tendencies characterize this specific model under review prompting, rather than the tools in their entirety.

Agent reviews are also inherently stochastic, and the scoring rules changed during the study. The repository archives five comparison files, described in \texttt{eval/results/README.md}. Two are complete, independent runs: \texttt{compare\_gates.json} and the final \texttt{compare\_gates\_round2.json} reported in Table~\ref{tab:gate-comparison}. \texttt{compare\_gates\_refined.json} re-runs only the eight non-REFUTED scenarios; \texttt{compare\_gates\_merged.json} consolidates the first run with that re-run and is not an independent run; and \texttt{compare\_gates\_final.json} is a run aborted by the account spend limit, whose INCONCLUSIVE entries from s13 onward are infrastructure blocks, not gate behaviour. Two scoring changes were made after the first run's results were seen: the agent-output parser was replaced by a decoder that takes the first complete JSON object, and the debris scenario (s06) stopped counting an accusation of the real debris as a false positive, counting one only when a look-alike file is named. The s06 change favoured the agent gates: under the first rule, all three were charged a false positive on s06 for finding the real debris. The parser change did not: in the first run, the baseline's answer on the honest s07 task could not be parsed and was recorded as INCONCLUSIVE, although its archived prefix reports \texttt{fraud\_detected: true}, so the final parser would most likely have scored it as a false positive. Scored as they were at the time, the agent false-positive counts in the two complete runs were 4 and 4 for nova, 4 and 2 for claude-wizard, and 4 and 5 for the baseline; applying the final s06 rule to the first run lowers each of its counts to 3 (4 for the baseline if its s07 accusation is counted), which gives the ranges in Table~\ref{tab:gate-comparison}. Re-scoring the final run with the final rules from its archived output reproduces every published status. The first run cannot be fully re-scored, because it archives only a truncated excerpt of each agent answer (at most 300 characters); the s06 answers fit whole, so that re-scoring is verifiable, while the s07 answer is cut off and remains INCONCLUSIVE. Kata yielded identical verdicts across every run, with zero false positives on these Kata-built fixtures. The agent reporting schema also lacked an explicit \texttt{UNVERIFIABLE} verdict, forcing agents either to accuse or remain silent, precluding explicit confessions of unobservable state.

The comparison, then, does not demonstrate general superiority of Kata over the reasoning capabilities of alternative tools. Rather, it isolates the core thesis of this paper: evaluating complex software engineering boundary conditions (such as Git commit ceilings, untracked ignores, and process exit codes) through heuristic LLM prompts forces the model to guess, whereas executing deterministic, code-level checks --- deterministic in the sense that the same repository state always produces the same verdict, not in the sense of completeness --- yields instantaneous, reproducible verdicts that confess blind spots explicitly. Whether this also means fewer false accusations on workloads not built alongside Kata remains untested. The comparison harness and raw records are archived as \texttt{eval/compare\_gates.py} and \texttt{eval/results/compare\_gates\_round2.json}.

\subsection{External evaluation: feasibility, scope integrity, and execution overhead on real repositories}
\label{sec:external-evaluation}

The trap suite is ours: the frauds, the fixtures, and the ground truth
were written by us, and a reviewer may reasonably ask whether the
mechanisms hold outside that self-referential setting. We therefore conducted
an external evaluation: 12 bug-fix tasks from six public repositories, attempted
by two models under two conditions (bare vs. kata, yielding 48 sessions in
total), with the JUDGE independently reviewing every final artifact. We state
upfront that this study serves to evaluate operational feasibility, scope
integrity, and execution overhead when applied to non-author code; with an
exploratory sample size of $N=1$ run per cell across stochastic agents, it is
designed as a feasibility and cost assessment rather than a statistically
powered measurement of model population effects.

\subsubsection{Protocol}

\textbf{Sample.} We selected twelve small fixes from public repositories
(Table~\ref{tab:external-tasks}); each is a real commit that fixed a real
issue and came with regression tests, so solvability is attested by history
rather than assumed. For each fix, the task state is the parent commit plus
the test files the fix changed, and the repository history is
re-initialized as a single commit so the agent cannot read the fix. We
verified for all twelve tasks that the selected tests fail in the task
state and pass at the fix commit (\texttt{python3
eval/external\_study.py -{}-check-tasks}).

\subsubsection{Results}

All 48 sessions produced a fix that passes the task's test suite, in both
conditions and for both models. The final artifacts contained no
weakened tests in any of the 48 runs according to the JUDGE's own
weakened-check detector, which found nothing to report. With $N=1$ per cell,
this is a single absence of a negative signal, not a rate: it indicates that
on well-isolated, narrow bugs with clear existing regression tests, these
particular sessions of frontier LLMs did not resort to
test-weakening tactics --- a result that describes these sessions, not the
models in general. Consequently, the external study demonstrates the operational
feasibility and scope integrity of the gate on third-party codebases, while
validation of the JUDGE's fraud detection capabilities rests on the 19 adversarial
trap scenarios of Section~\ref{sec:self-check} where frauds were actively planted.
The agent failure the external study did observe was
\emph{undeclared scope}: in one run (deepseek, bare), the session
changed \texttt{tools/intranges.py} to regenerate a code-point table but
declared only \texttt{idna/core.py}; the JUDGE flagged the extra file as
\texttt{scope\_creep} and returned VERIFIED WITH CAVEATS. The independent
review returned VERIFIED for the other 47 runs, with no false accusations
on any artifact.

Cost is the other side of this result; agent research has argued that
evaluation must account for cost, not only accuracy \cite{kapoor}, and the
same holds for gates. Without the cycle, the median session took 49\,s
(range 28--145\,s across all 24 bare runs); with Kata, 442\,s (range
104--1153\,s) --- the cycle adds a task file, the phase gates, and the
JUDGE to every change, and the median wall-clock cost is roughly nine times
higher (Table~\ref{tab:external-results}). The dispersion is substantial:
while no bare session exceeded 2.5 minutes, the kata arm developed a heavy
tail reaching 19.2 minutes (1153\,s on t08 for Claude, and 1040\,s for
DeepSeek), driven by iterative test-suite discovery, multiple verification
runs, and full coverage tracing across larger repositories.

This raises an explicit cost-benefit question: is paying a roughly 9-fold
median time overhead (and a 19-minute worst case) justified when the only
differential failure observed in 48 runs was a single undeclared file?
The answer separates the \emph{standalone reviewer} from the \emph{authoring
scaffold}. The JUDGE review itself is cheap and independent of the model
that produced the change: applied to the same final artifacts, it reached a
verdict in a median of about two seconds across all conditions (Table~\ref{tab:external-results}),
with outliers of about two minutes on t08 and fifty seconds on t10 where
the project's coverage command re-executes the full test suite. A review gate
costing two seconds per change is viable as an automated CI or pre-commit
check. In contrast, the full nine-phase authoring cycle (\texttt{kata --task})
is an interactive development discipline. On clean, well-isolated bugs with
clear regression tests (such as these 12 tasks), bare agents readily find
the direct fix without incentives to game visible checks. Whether the
authoring cycle pays for itself on complex or open-ended changes, where
verification is ambiguous and the incentive to game visible checks is
stronger, is a hypothesis this study cannot test: its tasks gave the agents
no such incentive. What the cycle measurably added here is an auditable
record (24 task files with Git baseline anchors), which the bare arm did not
produce.

This suggests two usage hypotheses for future evaluation, not guidelines
established by these data:
(1)~\textbf{Continuous integration and pull-request gating} with the decoupled verification gate (\texttt{kata --judge} or \texttt{kata --check-only}), which reviewed each change here in a median of about two seconds (at most 116\,s), subject to the evasions of Section~\ref{sec:threat-model}, the recreated anchor among them closable only by \texttt{kata --judge --trusted-base <ref>}, a CI-only ref the agent cannot move;
(2)~\textbf{Complex or autonomous authoring} with the full scaffold (\texttt{kata --task}) for open-ended, multi-file, or safety-critical changes, where the nine-fold overhead would have to be justified by effects this study did not observe.

The \texttt{kata} arm is also auditable after the fact. The 24 task files the
sessions left behind grade, under the audit mode of Section~\ref{sec:audit},
151 phase executions as followed, 13 as skipped (the documented headless
defaults) and one verify section as faked. Of the $24 \times 8 = 192$ phases
the audit schema covers (fit, think, intent, simplify, surgical, verify,
twins, and preflight), the 27 not counted are phases that were never
initiated in the YAML (neither \texttt{answered} nor \texttt{skipped}),
which the audit function skips; REPORT and ARTIFACT phases are not graded
by the audit. That single \texttt{faked} grade
is a practical false positive of the audit, and we report it as such: in
session \texttt{t05-kata-claude}
(\texttt{pycqa/pyflakes}), the session marked \texttt{success\_criteria\_met: true}
while all three objective checks (\texttt{ruff\_clean}, \texttt{tests\_pass},
\texttt{coverage\_pass}) were false, triggering the audit rule that flags
claimed success without supporting evidence (Listing~\ref{alg:audit}). The
session's \texttt{verify.notes} transparently documented the reason: three
legacy test failures in \texttt{test\_api.py} stemmed from Python 3.12
syntax-error message shifts, and \texttt{git stash} verified they failed
identically on \texttt{base\_commit} before any change. (In \texttt{t05-kata-deepseek},
\texttt{ruff\_clean: true} was recorded, satisfying the rule). The audit
grade is deliberately mechanical and context-blind: by design it cannot read
the notes, so it flags zero objective evidence alongside claimed success
even when the failure is pre-existing debt rather than fabrication. This is
the intended limit of the mechanism, not an unresolved defect --- the audit
names the risk, and the notes are what a human reviewer
reads to distinguish documented environmental debt from fabrication. The
24 session task files are archived
under
\texttt{eval/\allowbreak results/\allowbreak external\_study\_sessions/},
and the derived audit is archived in
\texttt{eval/\allowbreak results/\allowbreak external\_study\_audit.json}.

That deliberate blindness has a practical limit, though. When repositories contain
pre-existing test breakages or flaky suites, a context-blind gate flagging
\texttt{FAKED} on unverified success can create perverse incentives: developers
or agents may feel pressured to modify unrelated tests or bypass the quality gate
altogether. A promising extension, rather than a correction to the audit as
specified, is a formal mechanism for declaring
known baseline debt (\texttt{baseline\_failures}) at \texttt{base\_commit},
allowing the gate to certify that no new regressions were introduced without
penalizing pre-existing repository debt.

The harness field for the sessions' own JUDGE verdict
(\texttt{session\_judge\_verdict}) is null in all 48 runs because the harness
searched each session's text output for the CLI's \texttt{KATA JUDGE}
banner, which no session reproduces, instead of
reading the task files, which record the verdict. Twelve of the 24
\texttt{kata} sessions ran the JUDGE as their final step: six returned
VERIFIED, and six, all with \texttt{claude-sonnet-5} (t03, t04, t05, t06, t09,
t11), returned REFUTED, each for \texttt{spec\_betrayal} alone on an intent
disagreement the session had resolved and recorded. These are false
accusations of honest fixes: of the twelve sessions that reached the JUDGE,
half (6/12) were falsely refuted, a false-positive rate too high to read as
noise. Each session's own notes attribute the
verdict to the rule firing on any recorded disagreement. They come from the
behaviour of the evaluated JUDGE described in Section~\ref{sec:judge}, fixed
after the evaluated version in commit \texttt{15ccb7a} (shipped in 0.8.0); we did not re-run
the fixed JUDGE against these six sessions' artifacts, so whether the fix
would have returned all six to VERIFIED is stated, not measured. The JUDGE results in
Table~\ref{tab:external-results} are from the independent review pass, run on
synthesized task files whose intent section records no disagreement; their
absence of false accusations does not extend to the sessions' own JUDGE
runs.

\subsubsection{Caveats}

The external study is small and we do not over-read it. The twelve tasks
come from six Python repositories chosen for permissive licenses and a
pytest-based suite; they are not a random sample, and the fixes are
reconstructed from real commits (the bug is the parent commit; the
acceptance tests are the ones the fix touched) rather than open issue
reports taken verbatim. The repositories (\texttt{tomli}, \texttt{idna}, \texttt{pyflakes}, \texttt{more-itertools}, among others) are public and popular, and the fix commits are probably in the models' training data; re-initializing the history stops the agent from reading the fix in the sandbox but does not remove memorization. We did not use tasks dated after the models' cutoff or measure memorization, so the 48/48 pass rate may be inflated and bears on feasibility, not on capability. The acceptance tests were also pre-applied to the sandbox, which makes the task easier than a real issue. Two models with a single run per cell mean the
numbers describe these sessions, not the models in general; agent runs are
stochastic. Sessions that hit the harness timeout or the workspace spend
limit were re-run, and the study was resumed after the interruption;
only completed sessions are counted, and all 48 have status \texttt{ok} in
the raw results. The raw results do not record the number of re-executions
per arm; because the \texttt{kata} arm is roughly nine times longer than
the \texttt{bare} arm, it was more exposed to timeouts, but we cannot
quantify the selection effect without the re-execution log. The comparison is between two prompts to the
same host (the
Kata cycle and a bare prompt), with the bare condition running an isolated
agent configuration; it is a clean room for the tool, not for human
reviewers. The time difference between arms therefore reflects the cost
of the full Kata cycle (all nine phases), not only the JUDGE review. The independent review uses a task file synthesized from each
session's declaration and measurement, identical in shape for both arms,
so it exercises the scope and weakened-test checks; false completion is
outside its scope by construction, and the trap suite covers it. Last,
the review time we report is the automated JUDGE pass,
not human review time; and because no session in either condition weakened
a test according to the JUDGE's own detector, the external study exercises the
scope half of the JUDGE's
contract, while the weakened-checks half remains covered by the trap suite
of Section~\ref{sec:self-check}.

\section{Discussion}
\label{sec:discussion}

The 2026 preprints surveyed in Section~\ref{sec:field} --- on unreliable
agent self-reporting, benchmark confounds, and claim-based verification in
other domains --- are consistent with Kata's premise that a claim should be
re-executed rather than read. They are preprints, and we cite them as
context, not as evidence for the design. Kata applies the claim-verification
pattern to the software change itself, where the claims are the task file and
the ground truth is the repository.

The executed comparison of Section~\ref{sec:exec-comparison} sharpens
this positioning. All four agent gates detected every planted fraud, separating
\emph{detection} from \emph{restraint}: the difference appeared entirely on
honest and blind-spot scenarios. Detection did not require an executable core
on these fixtures, as prompted reviewers carrying the fraud taxonomy matched
code-executing gates. An executable core does not detect more on these
fixtures; it delivers a model-independent
verdict: reproducible outcomes, review times of 0.1--1.0\,s on the trap scenarios, and
honest confessions when mechanisms are unobservable. As analyzed in
Section~\ref{sec:exec-comparison}, agent false positives stemmed from
repository boundary conditions (\texttt{approved\_commit}, Git-ignores,
unprobed languages) where heuristic agents guess, whereas Kata programmatically
confesses blind spots as \texttt{UNVERIFIABLE} --- a verdict the agents'
reporting format did not offer, so this contrast is partly a property of the
comparison design. This reflects the
reliability-beyond-the-mean insight of the Double Measurement Confound
\cite{double-measurement}: agent false positives fluctuated across runs
(Table~\ref{tab:gate-comparison}), while Kata's deterministic execution
produced identical verdicts throughout, with no false accusations on these
fixtures.

The limitations of Kata are equally part of the picture. Kata is a
verification quality gate: it checks what was claimed against
real exit codes and the diff window it is given, within the threat model of
Section~\ref{sec:threat-model}, and says nothing about whether the generated
patch is optimal or complete beyond the declared checks. It is
interactive (falling back to defaults in headless mode); it requires Git;
and its success criterion is subjective. When project tests are flawed,
re-execution confirms a false oracle \cite{barr-oracle}, highlighting
metamorphic and property-based testing \cite{chen-metamorphic} as complementary
future work. The central claim of this paper is descriptive, moreover --- Kata
re-executes claimed checks and returns an objective verdict; causal evaluation
of whether the cycle improves AI-assisted code quality remains for future
controlled empirical studies \cite{fable}.

\section{Threats to validity}
\label{sec:threats}

The evaluation of Kata, like any tool evaluation, is subject to threats to
validity that we state explicitly.

\textbf{Construct validity.} The trap scenarios measure whether the JUDGE
detects planted frauds and does not accuse honest work. The construct
``fraud'' is operationalized as the seven categories the evaluated JUDGE
hunts (the current release adds an eighth), which
are derived from the failure modes documented in the Fable Method
\cite{fable} --- an unrefereed GitHub repository, so these categories are a
practitioner taxonomy rather than a validated construct --- and from the
reward-hacking literature \cite{specbench}. While
the trap suite demonstrates high sensitivity to these planted categories,
real-world bug fixes on well-scoped tasks (as observed in
Section~\ref{sec:external-evaluation}) rarely produce active test-weakening fraud
under modern frontier models, meaning the ecological validity of these constructs
remains to be probed on larger and more ambiguous industrial changes. The
zero-weakened count is circular: it is the JUDGE's own syntactic detector,
blind to a changed expected value, a loosened comparison, a swapped oracle,
tautologies outside its list, the deletion of a real Python assertion
(the probes flag only no-op removals by design, Section~\ref{sec:judge}),
and an indented comment that hides the assertion at non-zero column;
no manual inspection or mutation testing
supports it. A
fraud category not in the list (for example, a new class of weakened test
that the probes do not recognize) would not be detected, and the blind-spot
mechanism is the honest response: the JUDGE confesses what it could not
observe rather than claiming to have looked. The adversary is bounded as
well: the trap suite plants frauds in claims, not in all Git metadata.
s22 covers moving the anchor, which the reflog now detects, and s20 covers
the empty diff window; what remains outside the suite is deleting and
recreating the anchor, which erases the reflog and is demonstrated only by
manual reproduction unless a trusted base is supplied. The empty diff window
that the evaluated version produced when a task was approved before its
change was committed is fixed in 0.8.0 (commit \texttt{3cacc5a}) and guarded
by s20; the workflow that closes it after the commit is
\texttt{kata --stamp}.

\textbf{Internal validity.} The trap scenarios are deterministic fixtures
with a ground truth that specifies the exact verdict and the exact frauds
the judge must find. The harness fails when the verdict differs, when a
fraud is missing, or when an unexpected fraud appears. This determinism
removes experimenter bias from the evaluation, but it also means the
scenarios test what we thought to test. The honest scenarios
mitigate this: they encode false positives that were actually observed in
development (the debris false positive, the triviality-gate false positive,
the \texttt{.kata/} visibility false positive), so they are regression
tests for real defects rather than hypothetical ones. In the external
study, evaluating single runs ($N=1$) per cell across two models limits
statistical inference regarding stochastic variance in session execution
times, serving instead as a deterministic sanity check on the tool's behavior
across non-author code.

\textbf{External validity.} The evaluation is bounded in three ways. The
trap suite of Section~\ref{sec:self-check} uses small synthetic
fixtures authored by the developer rather than industrial workloads, with a
limited number of honest scenarios (four). The external study
of Section~\ref{sec:external-evaluation} evaluates real historical bugs
across six public open-source repositories, the tasks are intentionally small
Python bug fixes with existing pytest suites, evaluated with one run per
cell across two models. They demonstrate feasibility on non-author code and
restraint in the independent review pass, not in the sessions' own JUDGE
runs, six of which falsely accused honest fixes; they do not represent complex multi-file feature additions,
non-Python codebases, or proprietary enterprise software. A broader
multi-language study across diverse model tiers and task complexities
remains future work: the weakened-check detector is per-language by design
(Section~\ref{sec:judge}), so this generalization is not automatic and would
need language-specific probes validated the same way the Python ones were.
A third bound is the Gauntlet pilot's second campaign (Appendix~\ref{sec:gauntlet-campaign}, 30
sessions), which selects its five tasks by a measured gaming-incentive signal, but
draws them from the same pool of small, public, Python bug fixes as the
external study, and its blind A/B judge is itself an LLM, not an independent
human rater; the null result it reproduces should be read within that same
workload profile, not as a broader-population finding. The tool itself is also applied to its own repository: its changes are checked by its own lint, tests and coverage, and the trap suite runs in continuous integration on every push. We have no data on use outside the author's own projects.

\textbf{Author/evaluator conflation.} The author designed the JUDGE, wrote
the 19 trap scenarios and their ground truth, built the external-study and
Gauntlet harnesses, and is also the one reporting and interpreting all of
the results above --- no external party reviewed the trap scenarios before
they were run, and the ``blind'' A/B judge, while unaware of arm identity,
is not independent of the author's instrumentation choices (Section~\ref{sec:external-evaluation} and
Appendix~\ref{sec:gauntlet-campaign}). This is
declared in the Competing Interests statement, but it bears restating here
as a validity threat rather than a disclosure formality: every quantitative
claim in this paper is self-reported, and the zero-weakened-test findings
above are checked by the JUDGE's own detector, which is also the artifact
under evaluation (Section~\ref{sec:judge}). Mitigations in place are the
dogfooding on the kata repository itself, honest scenarios derived from real
observed false positives rather than hypothetical ones, and the executed
comparison against independently authored gates (Section~\ref{sec:exec-comparison});
what remains unmitigated is independent replication --- no third party has
re-run the trap suite, the external study, or the Gauntlet campaigns against
their own ground truth.

\textbf{Conclusion validity.} The claim ``the JUDGE catches fraud'' is
supported by the trap suite, but the claim ``Kata improves the quality of
AI-assisted changes'' is not directly measured. The mechanism is
plausible --- forcing evidence before approval, re-executing claimed
checks, and auditing completed work --- and it is supported by the
self-correction literature \cite{selfcorrect} and the reward-hacking
literature \cite{specbench}, but a controlled study comparing changes made
with and without Kata is needed to establish it.

\section{Conclusion}
\label{sec:conclusion}

Kata is not a skill. It is the tool that \emph{executes} the discipline that
skills ask for, and that distinction is the thesis of this paper. A skill is
an instruction; Kata executes the instruction. Where a skill
says ``verify your tests'', Kata runs the tests, measures the coverage,
compares it with the gate, and refuses to approve if it fails. Where a skill
says ``be honest'', the JUDGE re-runs the claimed checks and hunts eight
categories of fraud.

The evaluation demonstrates where the executable JUDGE succeeds as a
deterministic gate and where its boundaries lie. The 19 trap scenarios close
on the JUDGE's two-sided contract: every planted fraud is detected with the
expected verdict and no honest scenario is accused. The executed comparison of
Section~\ref{sec:exec-comparison} shows detection parity across gates. Kata
returned every expected verdict at approximately one second per review on the
trap scenarios (a median of about two seconds on real repositories), but most
agent false positives fell on blind-spot scenarios and on a Kata-specific
convention, so the comparison establishes determinism and cost rather than
superior restraint. The external study shows the JUDGE is feasible on real
repositories, and the judgment phases of the nine-phase cycle were not
ablated and were evaluated only for cost. An appendix reports an exploratory
pilot and a 30-session campaign that carried an iterative builder/critic loop
on the same task file and audit machinery. They found no evidence that the loop
improves the artifacts, with the direction against the cycle reversed between
the two and one run per cell, and their value is in showing how such a loop can
be audited and how the measurement has to be built. The evaluation still does not
show that the cycle causally improves the quality of AI-assisted code;
a controlled study of changes with and without Kata remains future work, and the
pilot's caveats (four tasks, ties in half the blind verdicts, a workload without
incentive to cut corners) say why it is not that study. Kata is an enforcement gate, not a panacea: it verifies claimed exit codes and diffs
rather than proving patch optimality; it is interactive; it requires Git; and
subjective criteria are accepted with explicit caveats.

For software engineering teams seeking objective assurance over AI-assisted code
modifications, Kata provides an executable enforcement boundary: it re-executes
claimed verification steps, confronts claims with the underlying repository, and
flags the claims that re-execution or the diff contradict, within the threat
model of Section~\ref{sec:threat-model}.

\appendix

\section{Exploratory study: an iterative loop on top of the cycle}
\label{sec:gauntlet-pilot}

The evaluation in Section~\ref{sec:impact} leaves the judgment phases unablated, and Section~\ref{sec:conclusion}
names a controlled study of whether the cycle improves the quality of
AI-assisted changes as future work. This appendix reports a first, explicitly
exploratory step in that direction: an implementation of an iterative
builder/critic loop on top of the Kata cycle, and a pilot that measures whether
it improves the artifacts. \textbf{The pilot finds no evidence of improvement}: on this
workload the loop did not produce a measurable improvement over the cycle
without it, and it lost to a bare agent in blind comparison, though with one
run per cell none of these differences is statistically distinguishable from
noise. We report it
because an inconclusive result from a pre-registered pilot is evidence about the method
and about how to measure it, and because the instrument corrections it forced
are reusable.

\subsection{What was built}

The loop follows the Gauntlet Loop pattern: an artifact is decomposed into
independently judgeable components; a fresh \emph{builder} improves one
component; a fresh \emph{critic}, in a separate context that never sees the
builder's reasoning, compares the real artifact against a concrete reference
(the \emph{bar}) and reports the single largest gap; the next round works from
that gap only, until the reference is met or a round ceiling fires. Two design
constraints limit what Kata can own here. The objective core of Kata is
deterministic --- it reads exit codes and Git state --- so the loop's execution
belongs to the agent host, not to the \texttt{kata} package; Kata's role is to
carry the loop's \emph{state} and to \emph{audit} it. The other constraint is
that a loop whose
critic runs in the builder's context is not the method: the independence is the
intervention, so it has to be observable.

Kata therefore gained three things, in a fork kept separate from the evaluated
version so the artifact of Section~\ref{sec:impact} is not disturbed:
(i) a \texttt{gauntlet:} block in the task file
(\texttt{bar}, \texttt{critic}, \texttt{boundary}, and an append-only
\texttt{rounds} list recording component, gap, verdict, and evidence per round),
validated on read with the same fail-loud discipline as the schema version;
(ii) an audit grade for it, so a declared loop with no concrete bar or no
per-round verdict is reported as \texttt{faked} rather than passing as
\texttt{followed}; and (iii) a \texttt{kata-gauntlet} skill, generated to both
frontends from the single source of truth, that orchestrates builder and critic
as subagents. Verdicts are binary (\texttt{pass}/\texttt{fail}): a numeric
scale invites score drift, where the number rises without the artifact
improving.

\subsection{Protocol}

The pilot reuses the external study's design of
Section~\ref{sec:external-evaluation}: real fixes from public repositories,
reconstructed from the fix commit with history re-initialized so the fix is not
visible, run headless by two models. It adds a third arm. \emph{bare} is the
model with no gate; \emph{kata} is the model running the cycle; \emph{gauntlet}
is the model running the loop, where the builder never sees the reference and
the critic is a separate subagent that does. Four tasks $\times$ two models
$\times$ three arms yielded 24 sessions. The reference for the critic is the
upstream fix commit, named in a file outside the measured tree; the builder is
never given its path.

Metrics and hypotheses were registered in the repository before collection
(commit \texttt{85eebf9}; a timestamp in our own Git history, not in an
external registry), following the calibration discipline the rest of this
paper practices. Of the five registered hypotheses, H4 (the loop costs more time than the
cycle) was contradicted by the pilot, and H1 (the loop is preferred to the
cycle) was supported in the pilot and reversed in the campaign, so it is not
supported. The metrics were: acceptance tests, weakened tests
(the JUDGE's own detector), undeclared scope, the JUDGE's independent verdict,
wall-clock cost, rounds and gaps per component, and --- as the primary metric
--- a \emph{blind A/B preference}: a fresh judge receives the two final diffs of
a matched pair with the origins hidden and the order fixed by a hash of
(task, model, arm) decided in advance, and returns a winner or a tie. The judge is \texttt{claude-sonnet-5}, which
is also one of the two models whose sessions it judges; we ran no
self-preference or position-bias check. When the two final diffs of a pair
are byte-identical the harness records a tie without calling the judge: this
happened in 7 of the 24 pilot pairs and 12 of the 30 campaign pairs, so the
number of judge calls was 17 and 18.

Two instrument defects were found during the pilot and corrected; both matter
beyond this experiment. The harness had measured ``tests pass'' by
running the manifest's \texttt{test\_cmd}, which for two tasks names a single
test file. Re-running the \emph{full} suite over the preserved artifacts
revealed a regression the narrow command had reported as a pass. The other
defect was in the A/B judge: it receives diffs but not the base state, so on
tasks whose
acceptance tests are pre-applied it cannot distinguish ``did not update the
tests'' from ``the tests were already there''. Both are corrected in the
artifact.

\subsection{A second campaign on a workload chosen for incentive}
\label{sec:gauntlet-campaign}

The pilot's caveat was that its tasks gave the agents no incentive to cut
corners, which makes it a poor setting for testing whether a quality loop
helps. To address that, three observable signals were defined and measured
offline, before any session: whether the acceptance test passes with the bug
still present; whether it asserts on fragile proxies such as message
substrings, counts, or snapshots; and whether the upstream fix touches more
than one source file. A task scoring high on these signals is one where
satisfying the visible test need not require fixing the cause. Applying the
signals to the study's task set selected five tasks (four of them
\emph{not} used in the pilot), and the campaign ran
$5 \times 2 \times 3 = 30$ sessions with the four instrument corrections in
place: the full suite measured as a delta against each task's pre-existing
failures, the A/B judge given the base state, sessions interrupted by the
ceiling or by a signal re-run rather than entering the analysis truncated, and
the workload selected by measured incentive.

\subsection{Caveats}

The pilot is small by construction and we do not over-read it. Four tasks give
N=1 per cell for a stochastic agent, and 11 of 24 blind verdicts were ties,
which limits discrimination. Two cells hit the session ceiling. Two tasks
decomposed into a single component, so they exercised no iteration. The blind
A/B judge sees diffs without the base state, which favours whichever arm
touched the test files; and in one of 24 judgments the judge stated it had
applied the diffs and run the suite, which it could not do --- a fabrication of
execution, recorded rather than discarded, whose verdict direction nonetheless
agreed with the independent full-suite measurement. We did not re-inspect the
other 23 judgments' stated reasoning for the same failure mode, so this
single confirmed case is a lower bound on how often the blind judge
misrepresents its own process, not a rate. The reference is the
upstream fix, which the measured tree does not contain, so the critic compares
against a description of the reference rather than the reference diff itself; a
critic noted this in its own gap. The workload is the external study's, finally:
clean, well-isolated bugs with clear regression tests, which gave the agents
little incentive to game visible checks --- the same condition that makes this
a poor setting for testing whether a quality loop helps.

\subsection{What scales, and what would have to change}

The pilot does not justify scaling the sample; it justifies fixing the
instrument, and those four corrections are implemented and archived alongside
the pilot. Each earned its place in the second campaign rather than in
argument: ``tests pass'' is measured with the full suite and reported as a
delta against the task's pre-existing failures rather than as a pass, because
the manifest's narrow test command had reported a regression as a pass; the
A/B judge is given the base state with the diffs, so that on tasks whose
acceptance tests are pre-applied it cannot mistake ``did not update the tests''
for ``the tests were already there''; a session interrupted by the ceiling or
by a signal is re-run with its attempt history recorded, instead of entering
the analysis truncated; and the workload is selected by measured incentive
rather than by convenience --- on three observable signals, whether the
acceptance test passes with the bug present, whether it asserts on fragile
proxies such as message substrings or counts, and whether the fix touches more
than one source file, the pilot's own task set scores low or medium, which is a
quantitative form of the observation that those tasks gave the agents no
incentive. With the corrections in place the campaign ran, and it again found no
evidence of improvement on a workload chosen for incentive
(Appendix~\ref{sec:gauntlet-campaign}). What the two studies
establish together is narrower and, we think, useful: that an iterative
builder/critic loop can be carried and audited by the same task file and audit
machinery that Kata already uses, that a blind A/B comparison with a
pre-registered protocol is needed to measure whether such a loop helps,
and that on the workloads measured here we found no evidence that it does, without power to exclude a modest effect --- while the measuring
pass itself has reusable value, having found and fixed a defect (a committed
artifact invisible to a moving \texttt{HEAD}) that neither study's results
would have revealed.
